# ScriptAct 并行评测与修复方案

状态：2026-09-30，根基修复与联合验收已通过，第 54 轮进入本机双任务槽并行接入。参见 [Platform 运行主链](../../../docs/architecture/platform-runtime.md)和 [当前执行状态](CURRENT.md)。

用户目标：以最快速度集中暴露和修复问题，在可复现、独立的任务上验证 ScriptAct 相对 Codex 等 agent 的优势。美元预算不再作为批次停止条件；质量、请求数量、整题耗时及总成本继续作为优化目标。修复必须针对通用根因，并防止对已测题目过拟合。

## 前置阶段：框架根基验收

先固定语言执行语义、持久对象强引用、资源句柄作用域、取消与提交、当前意图状态和长程查询合同。按审核报告的 owner 分工处理已确认缺口，用离线机制测试覆盖 GC/恢复、跨作用域、外部编辑、取消和提交后故障；先核实明细归账与模块/工具计数，再开放并发。产品候选与存储/执行协议在集成通过后封存。

本阶段完成之前，后续调度扩容和批量付费对照保持待实施。原始证据、历史尝试、费用及开发/独立任务归属继续保留。验收条件与逐项依据见根基审核报告第 6 节。

## 当前瓶颈

1. `budget-proxy.mjs` 的 `dispatchTail` 将所有 agent 的模型请求串行化，预算类仍拒绝超过 $1000 的上限。
2. `repository_launch.py` 要求整台专用 VM 和网关空闲；两套启动器固定单任务并发。
3. `report.py` 按时间窗口把共享网关请求归给任务；install-only 检查比较全局请求计数。并发前必须改成明确的任务身份归属。
4. 实测宿主为 10 核 / 16 GiB；Colima 为 2 vCPU / 6 GiB / 24 GiB，数据盘已用 93%、剩 1.8 GiB。宿主可用磁盘约 68 GiB。已核查的典型任务声明 1 CPU / 4 GiB RAM，当前只宜运行一个重型仓库任务。
5. 当前 VM 是 arm64，通过 Rosetta 执行 amd64 任务。新资源协议下双方都要重跑；不同机器或模拟层的旧耗时仅作历史参考。
6. 第 54 轮暴露快照含 192 条观察、26 个任务，已包括准备记录中人工预览参考补丁的三道题；这些任务按 development 管理。

## 并行分工

当前可同时运行主 agent 加三个子 agent。代码协作 agent 数量与评测 worker 数量分开管理。

| 负责人 | 独占责任 | 首批交付 |
|---|---|---|
| 子 agent A：调度与环境 | 网关、启动器、环境/制品准备、资源调度及对应测试；不编辑统计文件 | 可配置并发、任务租约、准确身份透传、取消和结算、资源槽位、源任务到全新容器判分的流水线 |
| 子 agent B：产品修复 | ScriptAct 运行时、上下文、展示/补读、项目编辑、Shell 相关实现及回归 | 从轨迹还原通用根因，最小复现、跨形状/能力/语言反例、独立补丁 |
| 子 agent C：证据与对照 | 暴露登记、报告、统计、缺陷台账；对应 `task_exposure.py`、`report.py`、`repository_report.py`、`metrics.py` | 并发记账核验、模块/工具调用明细与汇总、任务污染隔离、稳定基线、分层统计与置信区间 |
| 主 agent | 任务分配、接口协调、审阅集成、一次统一构建、版本封存和队列控制 | 分派去重问题、冻结候选、维护实验顺序，决定进入下一批次的条件 |

A 的基础设施稳定后，可将其重新分配到 B 的一个明确文件子域，继续平行修复；文件所有权交接由主 agent 统一完成。每个候选对应不可变产物；正在运行的候选不受新代码编辑影响。

## 第一阶段：先让并发结果可信

- 新 campaign 支持显式无美元上限的配置，保留费用账本、历史费用及未知用量；供应商限流、每题超时和资源限制继续有效。
- 网关改用有界并发调度，按实际 429、超时、排队及吞吐调整槽位。每个请求绑定 campaign / candidate / participant / task / attempt / request 身份，采用试验专属凭据或同等可信的映射，覆盖子调用、重试、取消和迟到结算。
- 新记录只按明确身份归属费用；历史串行记录保留既有口径。安装验收按本任务身份判断是否发起模型请求。
- 模块与工具调用同时绑定上述任务身份，以及会话、模型轮次、执行 ID 和调用 ID；并发任务、子 agent、重试与迟到回执能够准确关联，重复采集同一回执不重复计数。
- 每个任务独立工作区、容器、输出路径、租约与取消范围。镜像和固定制品可以预热；可变状态、提示上下文和工作树隔离。
- 使用可控本地服务同时发起请求，验证交错流、错误、重试、取消后的请求结束、进程回收、费用唯一归属和并发账本持久化；通过后派发真实任务。
- 继承完整暴露快照，冻结新候选及资源、模型和执行协议。

## 第二阶段：按资源容量跑批

最快方案是使用原生 amd64 Linux worker 池。建议以一台 16 vCPU / 32 GiB runner 的四个受控任务槽起步；若任务实际资源峰值、供应商限流和吞吐允许，再通过增加同规格 runner 扩到八个或更多槽。每题保留任务声明的资源和时限。正式速度比较采用相同且不超售的资源分配、平衡双方运行顺序，并单列系统排队时间。

本机可作为开发和集成节点。仅使用本机时，先扩盘，再评估将 VM 调整到 4 vCPU / 10 GiB / 48 GiB，从两个重任务起步；需同时检查 macOS 内存压力和磁盘余量。现有远程容量尚未确认，本提案不代表已创建或购买云资源。

执行顺序：

1. **已暴露接入组**：ScriptAct 与 Codex 跑完整双边链路，快速确认新调度协议和近期修复。首对采用已缓存的 Navidrome 仓库题，后续按语言、运行时和依赖类型扩展。
2. **24 题开发压力组**：从非 HARD 候选按仓库和任务特征分层固定选取，执行前明确标为 development。与旧题回归共同持续暴露问题；问题修复完成即可进入下一冻结候选，不等待不相关任务结束。
3. **稳定性复跑**：对预先确定的任务按相同次数重复，检验偶然性；重复次数不增加独立任务数。若当前难度不能区分表现，增加长程、多文件或依赖链更长的开发任务，保留较低难度的结果。
4. **独立确认组**：建议保留完整 HARD-51，加 55 道分层抽取的普通仓库任务，形成约 106 个独立任务的初始设计。最终样本量依据开发组方差和预先指定的效应大小确定，不把该数量当成必然足够的证明。

本地共有 642 个 SWE-bench Pro 任务 ID。扣除已记录的 12 道作业暴露题和 3 道参考补丁预览题后，有 627 个记录中未暴露的候选，其中包含 HARD-51 全部 51 题。这里只确认元数据候选池；镜像可用性、完整检出和未登记人工阅读还需核对。HARD-51 当前只冻结了题序，终验需要同时冻结整组候选、参与者和资源协议。

## 测试、诊断和修复同时推进

自动流程：固定候选跑批 → 保存完整轨迹与官方判分 → 以根因去重建卡 → 分给负责人 → 本地复现与修复 → 跨场景回归 → 主 agent 集成 → 新候选开发批次。

每张问题卡包含环境/候选指纹、原始轨迹位置、症状与根因、影响题目、最小复现、负责人和验证。普通解题失败进入台账，其余独立任务继续；任务间信息串用、错误归账、取消失效、冻结身份漂移和系统性判分环境损坏则阻断受影响队列。

按影响优先级处理：不能启动或完成、结果错误、重复往返和重复验证、上下文无效增长、工具/环境延迟、轨迹采集开销。缓存命中只作为解释数据，优化取舍依据整题质量、请求数、耗时和费用。

## 模块与工具使用统计

每次尝试必须回答：模型实际用了哪些模块、每个模块中的哪些工具/操作、各调用多少次。按单次尝试、任务、候选版本、参与者和整批汇总，保留主会话及子 agent 的分项和去重总计。

| 统计维度 | 必须记录的内容 |
|---|---|
| 模块 | 原始模块 ID、实际调用次数、使用该模块的任务数、涉及的操作种类数 |
| 工具/操作 | 原始工具名或 `module.operation`、调用次数、实际开始次数、成功/失败/取消/拒绝/未结束数量 |
| 时间与冗余 | 实际耗时总和、P50/P95、重试次数；有证据支持的重复读取、重复查询合同、重复验证分别统计 |
| 关联 | task、attempt、candidate、participant、session、parent、模型轮次、执行 ID、调用 ID、原始轨迹位置 |

计数口径：

- 模型声明可用、已导入或已查询合同的模块，与实际调用的模块分别展示；`modules.describe` 算一次能力查询，不算执行了被描述模块的工具。
- 模型外层工具调用、ScriptAct `execute/observe` 执行、底层模块操作分层计数。一次脚本调用五个操作，记为一次脚本执行和五次底层操作。
- 同一调用的开始、更新、完成事件按稳定 ID 合并；真正再次发起的重试另计一次。拒绝或校验失败不会冒充成功执行；未完成/无回执保持未知。
- 父任务与子 agent 的调用按会话和调用身份去重，并能分别查看。并行工具耗时总和与整题墙钟时间分列。
- Codex 等对照保留原生工具名称、外层调用和原生操作计数。跨 agent 可加“读取、搜索、编辑、命令执行、验证、记忆/上下文”等可解释分类；无法可靠映射的保留原名和未知分类，禁止把不同层级总数直接比较。
- 模型请求费用保留在请求层；同一请求涉及多个工具时，不把整轮费用重复记给每个工具。需要费用分摊时明确标注估算方法。

交付包括原始调用明细、模块汇总表、工具汇总表、各版本用量差异，以及高频、失败多、耗时高、疑似冗余操作列表。回归覆盖“一次脚本多操作、重复事件、同名工具跨模块、子 agent、并发、重试、取消和缺失回执”，并核对明细与汇总一致。

## 什么结果才足以称为领先

建议在执行前锁定两个不同结论，避免事后更换目标：

- **质量领先**：独立组官方正常完成通过率较某对照提高至少 5 个百分点，且经多对照和重复确认轮次校正后的配对置信区间支持提升。
- **效率领先**：质量达到预先声明的非劣标准，在共同正常成功任务上，请求数与整题耗时各降低至少 20%，总成本不增加；提升须得到置信区间支持。质量非劣容忍值建议严格控制在 2 个百分点内，所需样本量不足时明确保持未确认。
- **全面领先**：质量与效率同时满足约定标准。只达到部分标准时，结论限定于对应维度和任务范围。

完整报告同时展示所有尝试的成功率、失败、总费用、每成功任务总开销、请求数、整题耗时及 P50/P95；诊断层展示输入/输出/推理 token、上下文峰值、缓存读写、实际模块/工具使用及次数、工具耗时、重复读取、协议错误、排队与取消尾部开销。按任务配对、按仓库分层汇总，并保留基础设施失败的单独口径及用户实际经历的全流程口径。

终验候选在整组结束前保持固定。研发期间只查看执行健康与进度，题目级表现和轨迹在整组结束后揭盲；若用于下一轮修复，该组转为开发证据，新候选使用新的独立组。多轮确认预先分配显著性额度，避免反复终验造成结论失真。

现有统计是描述性比较，不能直接把 `supports_general_superiority` 改为 true；先实现独立统计层。通过标准是工程目标，不能预先保证实验必然给出 ScriptAct 胜出的结论。
