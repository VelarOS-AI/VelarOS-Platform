# 0017: 长程上下文按段追加、按剩余轮数封段

- Status: accepted
- Date: 2026-09-23
- Owners: Kernel、Model、Agent、Velaros Act

## Context

会话需要能持续运行，不应让用户换会话。现在的做法有三个问题：

- 按估算占用的 75%/80% 同步整理；
- 近期窗口按条滑动；
- 只保留一份历史检查点。

结果是：系统提示和历史每帧都在变，前缀缓存几乎不命中；字节估算比真实 token 大好几倍，整理来得过早；压力整理的派生结果按轮过期，任务内容量又只降不升，长跑时反复整理、越跑越窄。

## Decision

采用 [长程上下文](../architecture/long-running-context.md) 的设计：

- 请求按「系统提示 → 段底座 → 段内历史 → 本帧尾」排列，段内只追加。每帧随机标记和协议说明移到本帧尾，系统提示在会话内不变。
- 估算按供应商实测用量校准。整理时机改看剩余轮数与章节边界，不再按固定比例触发。
- 封段是确定性操作，不调用模型：历史封成不可变的卷，底座里的目录逐级合并。整理支线只在 `memory.organize` 或结构性超载时运行。
- 结果租约语义保持不变。
- 没有进展时分三级处理，最后一级暂停等用户，不停机；主线运行上限改为到点封段、继续运行；任务 token 总额改为速率上限加可选的用户上限。

## Alternatives

- **提高或调低比例阈值**：误差来自估算口径和滑动窗口，调阈值治不了抖动，也换不来缓存。
- **超出时开新会话**：打断用户，把连续性交给摘要，不符合「一个会话一直跑下去」的目标。
- **租约改为封段时才生效**：缓存略好，但段填得更快、封段更频繁，还要改动 INV-6、INV-10，所以没有采用。
- **按段固定随机标记**：可以省下每帧重发协议说明的开销，但段内写回世界的材料可能含有当前标记，削弱了「材料伪造不出控制段」的保证，所以没有采用。

## Security and privacy

每帧随机标记不变。授权代次、历史重置和 new 任务对段与卷的作用，与现在对检查点的作用相同；卷只记录引用和摘要，读回原文仍然经过现有的授权检查。

## Compatibility and migration

- 段、卷、底座都是新增的审计记录，旧会话打开时从第 1 段开始。已有的最新 `search:history-checkpoint` 转为第 1 卷。
- 整理补丁的 `history` 字段改为 `volume`，删除 `recentRecords`，由 velaros:context-materials 的生成声明同步。
- ContextStatus 新增 `runway`、`segment`、`cache`、`overload`、`stall` 等字段，保留原有字段；缺页明细和各分区占用在运行时的 memoryStatus 里（见设计文档「实现时的修正」）。

## Validation

每个阶段有对应的包级测试：

- 同一段内请求前缀逐字不变；
- 校准误差有界；
- 封段不调用模型，原文可召回；
- 目录条数有上界；
- 不会连续封段；
- 无进展时的三级处理。

另外，按现有门禁检查模块所有权、错误构造和 README 示例。

## Consequences

每轮输入里，只有本帧尾和本段新追加的部分按全价计费；其余部分走缓存，成本和延迟与已经运行的轮数无关。封段不依赖模型，长跑时不会因为整理模型失败而卡住。代价是每帧多发一份协议说明（约 1K token），并且新增三类审计记录。
