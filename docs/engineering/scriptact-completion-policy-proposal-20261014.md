# 完成判定策略调整方案（2026-10-14）

状态：已在 main 完成标准交付默认策略、显式独立复核入口与 failed 终态修复，完整 Desktop 构建和隔离设置验证通过。当前候选 v64 同时提供可配置状态预算（默认比例 1）与显式宿主 npm 导入；实际结果见[当前交付](./scriptact-current-state-delivery-20261014.md)。

## 问题与证据

修复前，Desktop 在启用项目工作区时自动装配 `model-review`。主执行提出完成后，再运行需求提取、产物定位和独立裁定；该链路失败会阻塞交付。`CompletionReview` 将异常映射为 `recovery: input`，Agent 随之进入 waiting；缺少用量导致的预算准入失败也走这一状态。

在同一 v58 的 d3-array 消融中，三方完整交付均通过。关闭复核 243.990 秒/12 请求，开启 524.495 秒/22 请求；开启组独立复核占 229.720 秒，没有带来后续修复。

新 eventemitter3 任务中，开启组 701.601 秒/26 次实际请求，关闭组 386.301 秒/13 次。两份 Runtime 产物都遗漏未知 Symbol 自有选项键；独立复核把对应 R5 判为 passed，之后因缺失用量占满预留额度中断。Codex 也受预算准入影响提前中断，三方完整交付均失败。额外审查在本例同时增加成本、漏掉语义缺陷，并引入新的交付阻塞路径。原评分器的覆盖缺口已在 main 修复，原冻结成绩保留。

这两组数据支持重新安排完成复核的职责；它们不证明关闭复核会提升所有任务的正确率。完整证据见 `completion-ablation-v58/conclusion.json` 与 `completion-policy-fresh-v60/conclusion.json`。

## 第一阶段：交付、实测范围和模型意见分别表达

1. **标准任务使用现有未验证交付合同。** 默认由主执行完成工作并提交答复，复用 `ContextCompletionResult.completed` 与 `verified` 的现有区分。没有领域验收证明时保持 `verified: false`。主执行仍须运行用户要求的实际检查，并在答复中报告命令结果与缺口。
2. **真实执行记录持续保存。** 实际命令、退出码、产物、错误和有效范围可追溯。完成主张、模型审查意见和具体检查回执按各自身份呈现。某条测试成功只证明它实际覆盖的行为。
3. **领域硬门禁继续生效。** 待结束执行、缺失必需证据、失效视图、显式领域验收器及有证据的失败保持原有阻塞语义。默认策略调整只改变 Desktop 自动安装独立模型复核的行为。
4. **独立复核作为明确选择的策略。** 提供标准交付与独立复核两种选择；选择独立复核时沿用现有取证、执行验证、取消和预算合同。复核报告明确标为模型意见及其实际检查范围。需要该模式的任务可在启动前选择。
5. **错误类型与运行状态对应。** 凭据、上游中断、预算不足、验证器协议错误分别保留原因和产物；waiting 只用于真实需要用户输入的情况。基础设施错误既不转换成验收通过，也不伪装成用户漏答了问题。

这一阶段复用现有 Context 完成状态和可选验证端口，不需要重做模型驱动或工具协议。主要改动位置是 Desktop 的 WorkspaceSession 装配、任务/设置策略透传和展示；异常分类落在 Runtime 完成复核与 Agent 终态边界。公开字段如需扩展，按仓库规则登记兼容版本、消费者及基线。

## 第二阶段：把验证工作放回实际修复循环

在新的独立任务中评估主执行是否能用少量、有区分力的实际检查覆盖用户约束，保留失败到修复再复测的连续证据。模型检查计划是待验证假设；实际执行产生结果。先做可关闭的实验，比较完整交付、误阻断、漏检、请求数、时间和缺失用量，不按已发现的 Symbol 题目增加专用提示。

长任务另外验收可恢复进度：L14 已按原期限结束并判失败。第一次 75 分钟整段运行约 38 分钟处失败，最后一轮在期限内不足 75 分钟，缺少合格的 productive checkpoint 和报告。保留产物功能检查 41/43，维护测试 20/20，其余类型、lint、浏览器和示例通过。现有 `goal.update` 已支持 blocked；最终模型如实说明缺口却调用 done，是已有完成决策的错误，需要继续实测。原硬期限及冻结账本保持原上限。

## 当前实现与实际验证

Desktop 高级设置提供“项目任务完成策略”，默认 standard；已有工作区的下一次提交读取最新设置。独立复核的基础设施失败返回 failed，并保留原因和 unknown 报告；外部取消仍走 cancelled。Context 0.10.0 和 Agent 9.8.0 已登记该公开联合类型扩展、锁文件和 API 基线。真实隔离 Electron 验证了默认值、双向切换及重启恢复，模型调用为零。

第一组 v61 Commander 实测：Runtime 339.283 秒/31 次请求，Codex 238.517 秒/27 次；双方正常结束，功能均 7/9。新增功能改变了原有可写且不可配置属性与 accessor setter 的兼容行为，双方完整交付均失败。保留维护套件分别 1371/1374 通过，其他类型、ESM、lint 和示例通过。默认策略的完成状态已实际可用；该结果没有证明质量改善。

对真实请求进一步分析发现，旧 Runtime 持续保留历史动态状态帧。v62 实验使用不可变用户/执行历史与末尾唯一当前状态，包清单明确宿主版本是后备安装。ShellJS 实测费用上升；QuickLRU 有界实验也未改善时间/费用，当前 default 为保留前缀的比例 1，并提供独立宿主导入。Runtime 全量 1086/1086、Desktop 会话 70/70、完整构建及设置验证通过。ShellJS 新题在付费调用前冻结 v61、v62、Codex 三条件及验收；结果记录在 `current-state-v62`。

L14 最终导出还触发原生字符串长度上限。当前导出改为流式写入和按哈希引用完整 turn，读取器兼容旧格式。对原始数据库零模型恢复了 149 个主 turn 和 60 个子 turn，完整哈希一致；恢复成功只修复记录链路，原任务仍判失败。
