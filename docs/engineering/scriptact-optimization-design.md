# ScriptAct 优化设计方案

状态：核心实现已落地，2026 年 10 月 1 日。本文说明设计目标与评估方案；最终接口和差量以 [实现与证据报告](scriptact-optimization-implementation.md)、[ADR 0026](../decisions/0026-scriptact-current-state-and-verification.md) 与现行合同为准。接口示意用于解释职责，准确类型以生成声明及宿主合同为准。

建议先实施当前工作视图，再调整能力与结果呈现，随后试点观察复用。核心目标是减少模型为运行管理付出的推理、代码生成和重复读取成本，使代码组合的收益转化为任务质量、总耗时和完整费用的改善。

## 设计目标

模型负责业务判断、临时组合和开放问题。Runtime 负责把已经掌握的当前状态表达清楚，领域负责稳定操作的语义和可以真实核查的结果。

每项优化都要回答一个独立问题：

| 优化项 | 要解决的问题 | 判断收益的依据 |
| --- | --- | --- |
| 当前工作视图 | 模型需要从多轮补丁重建当前状态 | 状态判断准确度、重复读取、整题费用和耗时 |
| 能力粒度与结果呈现 | 模型反复生成稳定的处理和失败判断代码 | 同质量下的生成量、恢复次数和整题成本 |
| 领域核查报告 | 成功叙述与真实产物之间缺少明确的核查范围 | 真实失败能否被发现、结果范围是否准确 |
| 有条件的观察复用 | 不变的观察反复采集 | 减少的真实调用及等待时间、时效与失效正确性 |

收益判断采用现有[验收口径](scriptact-acceptance-criteria.md)：先稳定性和质量，再总耗时与完整费用。请求数、缓存命中、字符数和脚本数用于解释原因。

## 整体执行结构

建议沿用现有执行主链，在三个位置调整：上下文呈现、领域结果核查、正常业务轮的观察准备。

```text
用户原文和现有任务状态
          ↓
Runtime 准备观察并取得真实回执
          ↓
ContextMemory 组装完整内部帧
          ↓
当前工作视图 + 已有原文历史 + 本轮必要正文
          ↓
ProviderRequestCompiler 核对实际请求和容量
          ↓
主模型提交 ScriptAct 程序
          ↓
Kernel 执行领域能力并记录真实效果
          ↓
下一业务轮；收尾时按宿主配置执行具体领域核查
```

主任务、搜索、业务子任务与整理继续由各自的真实能力范围和预算装配。具体所有权遵循[模块所有权](../architecture/module-ownership.md)和[运行主链](../architecture/platform-runtime.md)。

## 当前工作视图

### 数据来源与呈现

当前 `ContextMemory.project` 已经组装完整的分区数据，`ActiveContext` 已维护约束和未解事项。第一项优化主要改变呈现方式。

每个正常业务帧先给模型一份自包含的当前工作视图。这里的自包含指当前状态、条目身份和缺口清楚，不要求每轮重复全部原始材料。

| 内容 | 当前帧如何呈现 | 权威来源 |
| --- | --- | --- |
| 当前运行输入与目标 | 当前值和来源；用户原文、意图摘要分别标记 | 已有用户记录、GoalState 和输入投影 |
| 当前计划与工作笔记 | 当前计划；驻留笔记的版本、必要正文及原文位置 | 已有 task capsule 和工作笔记 |
| 有效约束与未解事项 | 当前有序条目，注明来源和核对状态 | 已有 ActiveContext |
| 待核对用户输入 | 明确列出 pending-review 与全文位置 | ActiveContext.pendingInputs 和原始输入 |
| 待导入历史来源 | 标明尚待导入的来源及其状态 | ActiveContext.pendingSources |
| 外部效果与执行障碍 | 部分提交、未知效果、失败和待处理项 | Kernel 回执与 Runtime 运行状态 |
| 必需材料缺口 | 当前缺项、原因、原文位置 | 现有 required 交付核对 |
| 活动作业 | 当前身份、状态及需要处理的结果 | 现有作业和子任务记录 |
| 观察与可见结果 | 当前身份、采集时间、正文位置、截断情况 | ProgramContext 和当前实际请求 |

列表每帧表达当前集合，模型无需应用 `splices`、`deleteCount` 或字段删除补丁。大正文、完整诊断和源码继续按首次交付、变更交付、冻结历史及引用召回组织。每项正文注明位于本帧、已选入历史或仅有引用。

例如，修改多文件配置后，本帧可直接表达：

```text
当前目标：修改指定配置并验证受影响路径。
有效约束：保留用户指定的配置项。
当前进度：两处修改已落盘；一项相关检查失败。
待处理：查看失败诊断后决定修复范围。
材料：失败诊断正文已位于本帧；修改原文在结果 R 的已发送历史中。
交付状态：执行有失败项；任务验收尚未完成。
```

这是呈现示意。实际文本由真实状态与有来源的模型笔记组成；Runtime 只渲染已有信息，计划与业务结论继续标为模型解释。

### 最小实现范围

在 runtime 内部从 `MemoryFrameDisplay` 派生当前工作视图，调整 `memoryPrompt` 的渲染策略。`ContextMemory.project` 先将当前驻留笔记的身份目录纳入内部视图，来源使用现有 residents 和段底座笔记快照；现有 notes 仅包含本段改过或新驻留笔记，单独据它重列会遗漏底座中的当前笔记。当前默认采用工作视图呈现；旧行为由实施前冻结源码保留用于对照，业务模型操作合同沿用现有接口。

`ActContextPort.delta` 仍承担同段请求延续的装配入口：新帧尾完整列出小型当前状态，原文正文使用现有变更判据。上一份已接受请求、段底座和有序历史继续冻结。这样可以复用稳定前缀，同时让最后一帧的当前状态易于理解。

同一字段只出现一种当前呈现。重复的帧 ID、目录元数据和低价值运行统计在 trace 中保留，进入模型的字段根据真实决策需要选取。先分别测量状态重列和元数据精简的影响，再确定默认集合。

### 容量与来源边界

当前工作视图使用现有分区配额并计入最终请求编译。软配额只裁剪允许裁剪的材料。约束、笔记和结果很大时，正文仍可能只够展示一部分，Runtime 必须保留条目身份、明确省略范围和原文位置。未决外部效果、失败与部分提交、必需材料缺口保持原有强制交付；必要状态放不下时进入现有超载路径。目录计数和省略范围用于可裁剪材料，不能替代必要障碍项。

当前用户原文具有既有权威。ActiveContext 和笔记继续是模型解释；尚待核对的输入保持待核对状态。用户纠正或撤销经现有来源核对发布后，当前有效视图直接表达剩余目标，历史原文仍按原存储保留。

工作视图中的引用只能定位材料。`required` 的满足条件继续来自本次实际请求中的完整正文或连续完整召回页；投影、实际历史选择、`reconcile`、完整响应接受及 `acknowledge` 的身份核对链继续有效。

### 核心验收

用真实 Runtime 链路验证多轮约束增删、取代、问题解决、列表重排、重复项和空集合，最后一帧能够表达当前行动状态。覆盖中途输入、重启、封段、权限重置和容量裁剪。

已有 required 交付正反例必须通过：摘要、引用、部分页、不同结果的相同正文以及退役历史均保持真实缺口。传输失败、协议修复和容量试探遵守现有基线推进与租约消费规则。当前视图变化应独立于原文冻结，实际请求和缓存断点仍可追踪。

## 能力粒度与结果呈现

### 能力设计判据

建议将能力分为三种用途，并由所属领域统一维护：

| 用途 | 合适的能力粒度 | 模型承担的工作 |
| --- | --- | --- |
| 临时组合 | 读取、搜索、计算、条件分支等基础操作 | 按当前问题组织程序 |
| 可靠业务操作 | 带事务、版本前提、取消和明确失败结果的操作 | 决定输入、处理真实结果 |
| 高频稳定组合 | 领域模板或经实测值得固化的高阶操作 | 选择组合、调整业务参数 |

除模型能否自行实现外，还要考虑重复生成成本、领域保证和恢复成本。具有事务或一致性语义的组合优先由领域实现；临时业务策略仍由模型组织。

### 第一批具体改动

| 能力 | 先做的调整 | 新增操作的条件 |
| --- | --- | --- |
| Project 和 Files | 模板准确说明各自的批量、事务与部分完成语义，优先使用已有批量入口；避免用循环拆散一次批量操作的语义 | 现有接口确实无法提供需要的领域保证 |
| Shell | 常用模板统一保留退出状态、后台状态和必要诊断，成功材料按决策需要输出；把管道阶段失败与无匹配区分清楚 | 有跨任务重复且可明确实现的稳定组合 |
| Office 等产物能力 | 提供所属领域的产物打开、结构核对与提交结果信息 | 检查必须依赖领域运行环境或可靠业务语义 |
| 搜索和跨能力数据处理 | 合同与模板让程序直接流转原始值，只交付模型需要判断的事实及范围 | 实测确认存在高频稳定组合，而现有模板仍需大量重复生成 |

第一批以已有合同和模板调整为主。每个高阶操作按操作职责进入所属单元的 `*Operations.ts`，由正式生成链产生声明、schema、效果和模板登记。稳定示例随所属模块发布；本会话程序可按既有 `sourceRef` 与 `input` 复用。

Files 的逐项原子写入、Project 的批量事务和其他领域的提交语义分别按真实实现说明。跨文件系统、网络与 UI 的组合沿用逐操作回执与部分效果报告。

### 输出处理

模型默认输出当前需要判断的材料。稳定状态与必要诊断优先通过已有领域结果和 Runtime 必要事实表达；大正文仍由脚本显式选择。对被筛选、分页或截断的材料保留来源和范围。

领域模板为常见结果提供简短、安全的处理方式。模板重点说明实际状态字段、失败含义和需要停止的依赖步骤，减少模型反复拼装解析与展示代码。每个新增模板照真实声明核对并在对应领域运行链上验证。

## 领域核查报告

### 复用现有完成机制

现有 `ContextCompletionPort.verify(view, signal)` 可以注入具体领域检查；未配置时允许未验证交付，配置且核查失败时进入既有有界修复。建议先让检查范围和原始依据通过现有 verification 事件清楚传递。

接口草案是在 `ContextCompletionResult` 上增加可选 `report`。下面展示拟议数据形状，当前接口尚无该字段：

```ts
interface ContextVerificationReport {
  scope: string;
  checkedAt: string;
  checks: readonly {
    label: string;
    status: 'passed' | 'failed' | 'unknown';
    evidenceRefs?: readonly ContextRef[];
  }[];
}
```

`scope` 说明实际核查范围。报告由领域的真实检查生成，作为不可变结果记录绑定逻辑 taskId、核查开始时的 GoalState.id/revision（有目标时）、检查时刻、实际产物和可获得的产物版本或内容指纹；无法取得版本时保留明确的证明范围。证据引用经过当前会话与权限范围校验。

`verified` 由宿主配置的具体验收条件决定。单个 check 的通过只证明该项实际范围；报告中的 failed 或 unknown 均如实保留。模型的 `done` 依据继续是完成主张，领域报告通过实际产物核查形成。

### 自动收尾的发布顺序

自动 done 路径先完成领域核查，再原子发布目标与任务完成。目标原身份及 revision 在核查开始时固定，防止旧证明被并发替换后的新目标继承。

核查开始时固定任务及目标身份。Runtime 准备目标变更与报告归属，Context 准备已经通过核查的任务完成数据；在同一个 ContextStorage 版本上，用现有元数据 CAS 或完整 CAS 一次发布目标记录、任务完成和成功报告。Context 接收中立提交数据，GoalState 的业务语义由 act/runtime 维护。实现时把现有验收与最终发布内部步骤分开，具体提交合同随该阶段的 ADR 一起审阅。

失败或取消保持真实核查记录，自动路径只有通过验收条件才发布完成。核查期间任务或目标 ID/revision 变化时，报告归属原目标，主线刷新后按新目标继续判断。独立的宿主 updateGoal/controlGoal 也参与最终身份核对。模型显式 goal.update 仍按该操作的独立合同处理。

### 两种使用方式

一般探索和问答沿用正常交付机制，报告已有验证事实和未核实范围。宿主对具体任务配置验收器时，验收器持有真实领域读取与检查接口，在收尾核查对应产物。

例如，代码任务可报告指定差量与实际运行检查的范围；文档任务可报告文件能否打开及所检查的结构；远端操作可报告服务端确认。具体检查条件来自任务或产品配置，并且在模型选择输出之前定义。

第一次实现先复用已执行检查与领域自带的轻量产物核对。新增昂贵检查必须有具体任务依据，检查时间和费用纳入整题账。

### 兼容与验收

可选字段允许旧宿主继续按已有 `completed`、`verified`、`reason` 和 `recovery` 消费。完整报告进入 context 记录，Agent 的 ActRunEvent.verification 同步增加可选 report 类型。Runtime 的 ActEventProjector 和 presentation 类型保留成功报告，供产品展示核查范围；当前工作视图表达范围与待处理项。报告上限登记在所属模块常量表，公开类型、README、invariants 和基线同步维护。

验收覆盖模型声称成功但实际检查失败、部分检查通过、检查无法判断、检查取消、用户改目标和产物再次修改。旧报告保留为原时刻的事实，新的产物与任务需要自己的核查依据。核查时效仅说明该报告的范围；与既往读取相关的全局资格判断遵循现行 ADR。

## 有条件的观察复用

### 启用条件

正常业务轮采集继续是缺省行为。先在宿主能够提供完整、可信版本信号的少量观察中试点复用，首选有单调 revision 的内部业务事实或存储。

宿主需要覆盖整份观察程序的有效输入与数据依赖，包括模块绑定、任务和可见范围变化。脚本对时钟、随机数、Shell、HTTP、MCP 或其他外部状态的依赖无法覆盖时，继续实际采集。具体程序的复用资格由宿主明确提供，模型声明自身只读或资源清单仅作使用意图。

普通文件 watcher 没收到事件，只能说明尚未检测到变化。首期复用以可靠版本为依据。源码或输入实质修改后，需要按新程序重新判断覆盖范围。

### 宿主接口草案

建议在 `VelarosContextOptions` 中增加可选的 observation 配置，由 act/runtime 接收。下面是拟议宿主端口形状，字段名称在合同实现时统一：

```ts
interface ObservationReusePort {
  probe(
    input: {
      sessionId: string;
      sourceHash: string;
      inputHash: string;
      scopeFingerprint: string;
    },
    signal: AbortSignal
  ): Promise<
    | { kind: 'versioned'; token: string }
    | { kind: 'unknown'; reason: string }
  >;
}
```

`scopeFingerprint` 绑定当前任务身份、观察相关模块实例及 generation、授权与可见范围代次。首期仅对宿主预先登记并核对过覆盖范围的观察指纹返回 versioned，其余返回 unknown；端口仅拿到哈希时，不能现场推断任意源码与输入的依赖。

`versioned` 表示宿主能提供覆盖该程序全部有效依赖的可靠代次。token 包含版本提供者的生命周期身份，提供者重建或计数归零后与旧 token 区分；代次变化必须可检测，包含期间发生变化又恢复原内容的情形。`unknown` 表示继续实际采集。这个端口只服务采集决策。

### 采集与复用流程

1. 轮边界合入用户输入，取得当前观察源码、输入和范围身份。按既有健康机制处理 paused。
2. 有复用端口时进行有界探测。探测返回 unknown、失败、超时或范围变化时实际采集。
3. 相同源码、输入、范围和可靠代次下，只有完整成功的上次采集结果可以复用。宿主还可配置最大复用年龄作为保守兜底；年龄本身只表示时效。
4. 实际采集前后均取得可靠代次；两次提供者身份及 token 一致，且本次完全成功，才保存复用基线。采集中发生变化或覆盖变为 unknown 时照实展示结果和时间，下轮继续采集。
5. 失败、部分采集、捕获问题和未知效果沿用既有健康与回执机制。

复用保留原 `resultRef`、执行身份和采集时间。帧仅增加简短的 collected 或 reused、年龄和刷新原因，trace 记录探测及复用决定。能力调用与实际脚本执行按真实发生次数归账。

图片等附件沿既有授权链读取；无法恢复时按真实缺口处理，满足运行条件后重新采集。进程重启后，健康机制允许运行时先实际采集一次，再建立新复用基线；旧结果仍显示原采集时间。

模型请求当前状态时，可通过拟议的 `observe({ sourceRef, refresh: true })` 请求下一正常业务轮实际采集。该选项随控制声明注册表、参数核对、协议说明和测试统一维护。只有整份响应被接受后请求生效，协议修复轮沿用原帧。刷新请求遵守现有 paused 恢复条件。

阶段性观察可使用现有 observe 更新或 clear。首期将“什么事实还需持续观察”写入相应模板的业务用法，按已有程序版本管理生命周期。

### 试点验收

稳定代次下真实调用减少；变化、范围重绑、源码和输入修改会采集新结果。覆盖探测超时、丢失变化信号、采集期间变化、变化后恢复原内容、重启、图片丢失和采集失败。freshness 信息只影响采集与展示，写入和完成继续按各自现行合同处理。

若获取代次的成本接近实际观察，或合适的业务覆盖范围很小，观察复用保持按场景配置。是否扩大范围由真实任务收益决定。

## 实现所有权与合同影响

| 所有者 | 拟议改动 | 主要接入位置 |
| --- | --- | --- |
| act/runtime | 当前工作视图、自动完成发布、观察准备与复用状态、核查结果展示 | ContextMemory、ProgramContext、RuntimeSession、SessionGoal、ActEventProjector、runtime 的 types 与 requires |
| act/system | 继续提供模型的计划、笔记和材料管理；按需要精简使用模板 | 已有 Operations、合同与模板 |
| Agent | 实际请求延续、真实历史选择、容量与 verification 事件合同 | ActLoop、ActContextPort、ActRunEvent |
| Context | 可选领域核查报告、验收与完成提交边界、不可变结果记录 | ContextCompletionResult、ContextCompletionPort、ContextViewSession |
| 领域能力 | 批量语义、稳定组合、实际产物核查和版本信号 | 所属单元 Operations、requires 与模板 |
| Model | 继续编译实际文本与图片请求并真实计量 | ProviderRequestCompiler 与现有适配器 |
| 产品宿主 | 选择试点配置、提供版本信号和领域核查、展示验证范围 | 产品 Runtime 装配与结果展示 |

第一阶段可以只改内部模型呈现。可选报告、观察宿主端口与 refresh 控制选项分别作为独立合同变更审阅。需要公开新类型时，按 provides、包 exports、基线和宿主兼容要求处理。

模型可调用的领域新操作始终从 TS 操作接口生成。变更公开合同、持久状态或运行语义时补充 ADR、对应不变量和差量报告。边界检查沿用现行 [ADR 0020](../decisions/0020-no-host-reconciliation.md)、[ADR 0021](../decisions/0021-no-decision-basis-write-gate.md) 和 [ADR 0025](../decisions/0025-no-completion-read-check.md)。

## 实施顺序

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| 第一阶段 | 冻结当前基线；实现当前行动状态每帧重列，正文沿用已有交付 | 来源、容量、required、缓存延续和租约回归通过；固定任务对照完成 |
| 第二阶段 | 独立精简重复元数据与使用说明；调整现有领域模板和常用合同呈现 | 在同质量任务上证明重复生成或读取减少，完整成本没有被转移到其他步骤 |
| 第三阶段 | 可选领域核查报告；先核查后自动发布完成；接入少量真实产物检查 | 失败、取消及目标竞态正确；报告范围准确；检查成本可核对；宿主兼容验证通过 |
| 第四阶段 | 在有可靠代次的场景试点观察复用和显式刷新 | 失效与恢复完整通过；实际减少调用和等待时间；领域能兑现覆盖承诺 |
| 第五阶段 | 组合经过验证的优化，决定默认配置与适用任务 | 冻结独立集满足已登记的稳定性、质量、耗时和完整费用标准 |

每阶段形成独立候选。先冻结源文件、构建产物和配置，再运行；候选运行期间保持封存。失败结果、修复前数据、未知用量及恢复成本完整保留。

重开旧会话时，首帧按当前呈现策略完整组装，已冻结记录与真实请求快照保持原文。旧观察没有可信复用状态时按正常轮采集。旧宿主继续消费原完成字段；新的报告是可选增量。

## 评估设计

### 机制对照

首先比较当前上下文呈现、当前行动状态每帧重列、整个分区完整重发三组。在相同内部状态与能力下，检查收益来自状态更清楚还是材料重复更多。

随后独立比较元数据精简、模板调整、领域核查及观察复用。每组固定模型、上游、任务初态、资源、预算和其他配置。优化改变了执行次数时，归账保留全部实际尝试。

上下文核对可先用真实 Runtime 的零模型链路验证机制和竞态；模型能否更好判断当前状态，需要独立模型任务验证。领域核查用实际产物验证，观察复用用真实代次和真实调用计数验证。

### 任务覆盖与指标

预先冻结未暴露任务，覆盖编程修改、结构化数据处理、跨能力资料流转、浏览器或产物操作，以及长任务中的用户纠正和外部状态变化。开发题用于诊断，独立集用于判断默认设计。

优先报告全部计划任务的成功、失败、超时和未知状态。双方成功的配对用于比较成功效率；全部任务的耗时与费用另外报告。各候选分别统计，使用相同模型与资源，保留实际样本数和不确定性。

除完整费用与总耗时外，诊断数据包含：模型生成与推理量、输入与缓存读写、正文重读、状态误读、协议修复、领域失败、维护调用、观察实际调用和探测成本。报告单次机制是否真正触发，原始真实用量和实际扣费分别列出。

单题改善支持诊断和回归。默认启用的依据来自事前登记的冻结独立集；机制没有触发的任务保持相应标记。某项改动只在一类任务有效时，将其作为该类任务的配置。

本次已实现当前视图、领域模板、可选核查报告、原子自动收尾与可信观察复用，并在文档索引登记。具体合同差量、已通过验收、冻结对照与真实模型证据见 [实施报告](scriptact-optimization-implementation.md)。更大独立任务集和单机制消融仍是继续判断默认策略与推广范围的验收工作。

每阶段实施时同步 README、invariants、生成声明和模板，差量报告逐项说明合同变化、理由及影响。按改动运行所属包检查；模型操作变更运行 `generate:script`、`check:script` 与相关 Act catalog 检查，读取构建结果的检查先构建对应包。每轮运行 `bun run check:module-ownership`。
