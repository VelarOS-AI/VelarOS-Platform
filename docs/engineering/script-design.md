# 代码面：模型用写代码的方式使用能力

> 2026-09-17 立。用户裁决：押注模型的代码能力，把能力面从 provider 的 tool-calling 规范升级成一套自有的 TypeScript API。
> 本文讲能力面怎么设计：为什么写代码、声明怎么生成、能力怎么给模型。模型怎么交程序、Runtime 怎么跑，以 [文本协议](../architecture/scriptact-text-protocol.md) 与 [运行主链](../architecture/platform-runtime.md) 为准。
> 2026-09-18 的「门」是四个脚本工具加一条脚本时间线（当天先是一个 `program:run`），2026-09-20 随 `packages/code-surface` 整包删除（342be1f2）；下文涉及它们的段落已按现行实现改写，原样见 Git 历史，早期实施过程记在 `foundation-refactor-log.md`。

## 为什么

今天模型面走 provider 原生的 tool-calling：一次把所有工具定义摆上去，模型吐一个 `{name, input}`，宿主执行，回执整个进上下文。
这套规范的三条限制，在这个仓库里各长出了一套补丁：

| 现有机制 | 它在补的限制 |
| --- | --- |
| `tooling:map` / `tooling:read` / `tooling:replace` 整套工具空间分页 | 所有工具定义必须一次性全摆上。browser 32 个工具 = 14,153 字，每轮都在 |
| 各工具的 `files[]`、`steps[]` 批量字段与「一个批量维度」的规矩 | 一次往返太贵，只好把循环塞进参数里 |
| 结果截断、当轮句柄化、`distill_context` | 每个工具回执都必须整个进上下文 |

代码面把这三件同时解掉：工具空间分页变成 `import`，批量变成 `for`，中间结果可以在程序里过滤掉、只把要的交出来。

还有一条更根本的：**说明是第二个真相源**。今天的模型面说明是手写的，实现改了它不会跟着改——本轮修的四条缺陷
（`op="read"` 枚举里没有、`nextActions` 字段不存在、`version` 实为 `revision`、`statusContinuation` 少一层嵌套）全是这个病。
最能说明问题的是 `system:read`：结果类型里有 `hasMore: boolean` 直接回答「读没读完」，而手写说明教模型拿 `range.end` 自己推算，
`hasMore`、`totalChars`、`encoding` 三个真实字段模型从来不知道存在。声明从源码生成之后，这一类缺陷在编译期就炸。

## 定下来的

1. **模型写 JavaScript，执行之前只查语法**（2026-09-26 起，[ADR 0019](../decisions/0019-scripts-check-syntax-only.md)）。不自造语言——
   这件事唯一的依仗就是模型见过海量 JS/TS；自造语法等于把依仗扔掉。「自己定义规范」定的是 **API 表面与调用约定**，不是语法。
   写 JS 而不是 TS，中间**不必转译**，于是转译带来的行号错位整块消失——那正是这一版最先出 bug 的地方。
   检查只做 JS 引擎本来就会做的：语法（输出被截断时当场就炸）、每个 import 落得到、要的导出名模块里有（和 ES 模块链接时一样）。
   早先照声明做 `checkJs` 类型检查，真跑长任务时它把对的程序一轮轮弹回去（空数组推成 `never[]`、字面量拓宽），用户裁决拿掉；
   字段名写错读到 undefined，入参形状错由 Kernel 按 schema 在那一次调用上拒绝，报错写明哪个字段错在哪。
   手滑写了 TypeScript 不废掉一整轮：整份诊断都落在「这个语法只能在 TypeScript 文件里用」那一族时，
   按 TS 再解析一遍（真语法错照样拦），剥掉类型照跑，并在回执里提醒它下次写 JavaScript。
2. **原生协议压缩到只剩文本。** provider 那层去不掉（模型总要吐出点什么、宿主总要收到点什么），现在它只传文本：
   模型在普通 Markdown 里用本帧随机标记框出程序段——`observe` 稳定观察程序、`execute` 一次性程序、`blobs("名称")` 不进源码的原文、`done` 申请完成；
   供应商请求里没有业务工具表，也没有 JSON responseFormat（[文本协议](../architecture/scriptact-text-protocol.md)）。能力一律在脚本里 import。
   （2026-09-18 时是一扇只有四个工具的门：`script:exec` 跑、存、重放，`script:history`、`script:show`、`script:diff` 读时间线，2026-09-20 删掉。）
3. **声明从源码生成。** 能力包的入参与**出参** TS 类型 → 模型读的 `.d.ts`。生成物进仓，门禁守着它与源码一致。
   出参这一刀最关键：今天回执根本没有 schema，所以回执类缺陷只能靠人眼抓。
4. **执行前先查语法。** 语法错、import 落不到的程序回灌诊断，一行不执行。
   诊断**必须带代码帧**：模型吐出来的程序是一段裸文本，它自己看不见行号，只回「(2,29)」等于让它靠数行定位。
   导出名写错时说明后面接上这个模块实际导出什么——猜得离谱的名字只说「没有」，模型只好再猜一轮。
5. **改已有的代码不必整份重写。** 每处是 `oldText` 换 `newText`：`oldText` 一字不差、在整份底稿里唯一，一组全成或全不成、
   各处不许重叠；不唯一就多带几行上下文。**不用行号，也不用字符位置**——模型看不见自己写过的代码的行号与偏移
   （早先留过一个按字符偏移收窄的 `range`，模型根本算不出那个数，删了）。
   底稿是本会话保存过的任何一版程序：当前观察版本（observe 不给 `sourceRef` 时就是它）、之前 execute 的源码，
   或者检查没过时存下的草稿（`draftRef`），用 `sourceRef` 指它（[增量编辑](../architecture/script-incremental-edit.md)）；
   指到不是本会话保存的东西时明确拒绝（`SCRIPT_REF`），**不猜一份出来**。
6. **代码跑在子进程里的 QuickJS（WASM）上，它自己没有任何能力。** 每次 API 调用经能力桥回宿主，审批与危险判定还在原来那道端口后面；
   QuickJS 里够不着 process、require、fetch、WebSocket（script INV-5、INV-9）。
   **不用 `node:vm`**：模型写的代码可能被提示注入影响（浏览器页面内容能诱导模型写出恶意代码），
   `vm` 挡得住「够不着」，挡不住有心的逃逸。子进程顺带白拿超时与取消。
7. **审批下沉到 API 实现内部。** 今天「危险命令硬门化」成立，是因为一次调用就是一个可审查单元；
   代码块里几十条语句不是。解法是同一道端口在 API 函数实现里撞，而不是在协议层撞。
   现在就是这样：危险命令的确认经 Kernel 的 `ApprovalPort`（宿主不给就一律拒绝），脚本停在那次调用里等，程序时钟停表（script INV-18）；
   确认界面由宿主实现这道端口。
8. **中间结果不自动进上下文。** 只有 `output` 交出的、导出的值与 `console.log` 的输出进；要看多少由模型在程序里定。
9. **每次 API 调用发运行事件**，界面照旧显示卡片。
10. **旧的 tool-calling 面已经删了**：各能力包的工具 2026-09-18 换成代码面的操作、原包直接删掉；agent 里的工具执行器与工具空间分页
   2026-09-22 随 Agent 4.0 合同迁移删掉（71fa202a）。原计划是留到代码面在 agent-lab 上打平再删——
   **没有对照就没法证明赌赢了**；删的时候仓库里没有这轮对照的记录，现在的效果看 `bun run eval:act` 的真实任务评测（[长任务与评测接入](act-long-run-eval-delta.md)）。

## 哪些东西进模型可观测面（`@AgentView` 与双向门禁）

**问题**：改 `SystemReadFileResult` 的人，在编辑现场看不到任何迹象说明模型在读它。
可观测面靠「从操作方法可达」隐式决定，这是最容易出事的一类无形契约。

**根**由登记表声明（命名空间 → 接口），并且**每个放出去的方法要打 `@AgentView`**——
同一个接口里可以只放出一部分，不是全有全无。

**闭包由机器算，不手工维护**（手工标一定会烂），但闭包里的每个类型**必须带 `@AgentView`**，门禁双向守：

| 情况 | 门禁 | 为什么 |
| --- | --- | --- |
| 在闭包里、没标 | 红，并列出要加标记的类型名 | 你让一个类型进了模型可观测面，得知道 |
| 标了、不在闭包里 | 红，让你删 | 免得标记烂成装饰 |

这样标记不可能过期：加一个字段引用了新类型，门禁当场告诉你「它进模型面了」。
与仓库既有的 `check:agent-public-api`、提示词指纹是同一套路子——生成物进仓，改了要重算并说明。

### 一条规则两处用：标记**之后**的才是模型面

标记打在方法上时它就在第一行，整段说明都进模型面——这是今天已经在做的事。
把同一条规则用在**操作接口自己**的头部，就多出一个位置：标记之前写给我们自己看的话
（实现类叫什么、进程里有几份），标记之后写**整个命名空间都成立**的事，它成为生成声明里的模块级注释。

这补上了一个真实的盲点：`system` 的「位置一律按字符算，没有行的概念」「写是原子替换」本来只写在接口头上，
**模型一个字都看不到**，而这些恰恰是它最容易踩错的。
放进模块级注释之后，三个方法各自的说明里那几句重复的话也就删掉了——不重复说废话。

### 声明里一律写原生形式

源码里为我们自己方便的写法，到模型那边都是要背的间接，生成器一律展开：`Nullable<T>`、`Optional<T>` 这类仓库别名写成 `T | null`、`T | undefined`；
`type K = (typeof Ks)[number]` 这种从词表常量推出来的类型，就地写成字面量联合 `'a' | 'b'`，常量本身不抄进声明——
模型拿不到它，照抄过去只会让它从字段跳到类型、再跳到常量才知道能填什么。所以词表常量不用打标记，标记打在类型别名上就够了；
源码里常量仍是运行时的唯一权威（宿主据它校验），类型照旧从它推。

### Act 与标准模块走同一条路（2026-09-23）

`velaros:system`（goal、modules、memory、store）、`velaros:context-materials`、`velaros:search`/`velaros:evidence`、`velaros:agents`/`velaros:interaction`
原先手写 JSON Schema，声明再由 Kernel 从 schema 合成，模型看到的是 schema 的投影，出参与说明都对不上源码。现在和领域能力一样：

- **合同在操作接口上。** 各职责组的 `impl/*Operations.ts` 写接口（`@AgentView` 模型文档、`@OperationEffect` 效果、`@OperationModes execute` 只能在 execute 里用的写操作），
  `scripts/script/surfaces.mjs` 登记，生成器写出 `contract/surface.ts`；`impl/*Module.ts` 只把生成的模型面与实现绑成 Kernel 模块（宿主上下文、读取登记、效果核对、写入前拒绝的错误标成无效果）。
- **一份实现、几种投影。** 同一个实现类按装配挂不同的接口组合：store 的创建/读写/只读三种，memory 按有没有长期记忆、有没有整理模型分四种，一种投影一份生成的合同，一共 14 种（`packages/velaros/act/README.md` 的目录由生成器从合同写出）。
- **生成器补的三件事。** 入参写成 `input: Optional<X>` 就是可以不传（宿主上下文排在后面，TS 不许写 `input?`；声明里印成 `input?: X`，派生 schema 是 `null | X`）；`@OperationModes execute` 生成 `allowedModes`；
  类型按符号解析，dist 里的 `.d.ts` 映射回同包源码，一个闭包里出现两个同名类型直接报错——早先按名字找曾把 project 的 `SearchResult` 当成搜索的那个。
- **标准模块也生成。** `velaros`（output）与 `velaros:program`（input、blobs）的声明由 script 包 `types/standard.ts` 的接口生成（`StandardSurfaces`），不再手写声明字符串。
- **支线交付是普通操作。** 搜索子会话用 `velaros:evidence` 的 `report` 交报告，整理子会话用 `velaros:context-materials` 的 `submit` 交补丁，都过 typecheck；无类型的 `tool.report(output)` 钩子删了。
- **上限写在文档里，数字只有一份。** 派生 schema 只管形状；数值上限写进 `@AgentView` 文档，数字来自所属单元的常量表，入参核对引用同一份常量，
  验收逐条核对声明文字与常量（先例是 files 的 INV-10；act system INV-20、search/agents INV-2、context INV-13、script INV-37）。
  script 的 `validateOutputOptions` 要整段注入隔离堆、不能引用常量表，它的边界由 INV-37 在常量上放行、常量加一拒绝。
- **还留着 schema 的只有两处。** MCP 工具：外部服务器只给 JSON Schema、没有 TS 源码可生成，声明由 Kernel 从它合成——这是唯一从 schema 出声明的地方；
  browser/office 的 zod：是操作自己的入参核对的写法（上限同样引常量表），模型看到的仍是 TS 接口生成的声明，zod 不进模型面。

## 能力怎么设计：组合交给模型，工具只做必要的与绕不开的

这是代码面上设计每一件能力的判据（你定的）：**尽量把组合和操作交给模型，工具只提供必要的能力，
以及模型做不了、交不出去的那部分。** 不要替模型把链路想全——它有自己的想法，给对原语它自己会组合。

拿「看图」做例子，只有两件是工具非做不可的：

| 谁做 | 做什么 | 为什么 |
| --- | --- | --- |
| 工具 | 把像素交到模型眼前 | 只有宿主能把图放进上下文；图走结果旁边的通道，程序拿到的只有尺寸 |
| 工具 | 把超限的图压进 API 上限，按要求裁一块 | 隔离进程里没有图像编解码；上限跟着 provider 走，模型不知道 |
| 模型 | 看哪几张、看不清时放大哪一块、要不要分块、看完记什么 | 这些都是组合，给了 `region` 它自己会想到 |

所以 `view` 只收 `{ path, region? }`：在上限以内的图**原样交出**，超了才压，要了 region 才裁。
我起初还设计了 `imageInfo`、`maxEdge`、token 计数——都砍了，那是替模型把链路想全。

上限对齐官方文档（不是记忆）：一个请求超过 20 张图时每张都不得超过 2000 px，所以默认长边 2000；
API 按 **base64 之后**的大小限（直连 10 MB、Bedrock/Google Cloud 5 MB），所以默认 5 MB，按 base64 算——
原来按原始字节限 5 MB，5 MB 的图 base64 后 6.7 MB，走 Bedrock 会被拒。
一次程序最多交 20 张。**图只给模型看一次**：agent 历史层里，最后一条助手消息之后的工具结果（模型还没回应的）才保留原件，
模型一回应，那些图在之后的每个请求里都换成占位——不因为是「最近一条」就一直挂着。要再看就重新读，
读一次的代价远小于一直带着它；那行「图片 1/1：某文件」的文字说明留着，模型知道自己看过什么。

### 代码模版不能省

我们知道这些能力怎么组合，模型未必知道。每个命名空间一份模版文件（能力单元里是 `packages/velaros/<单元>/template.js`，一个单元出两件能力时另一件的叫 `<模块>-template.js`（`packages/velaros/project/code-template.js`）），
**import 只写一次**，下面一段一个函数、一种日常最常用的写法（跑测试只交失败的尾巴、改一行配置、搜到就改、看过差量再落回……）。
**模版只是示例**：模版头与能力使用说明里都写着按需要改写、不必照着写——它教的是能力怎么组合，不是程序必须长成这样。
没有模版的命名空间生成器不给过。写错的模版会把错的写法原样教出去，所以有两道核对：各单元的验收把模版**整份照真实声明过类型检查**（`codeProgramChecker.typecheck`，模型交的程序不走这条）；
仓库层的 `tests/capabilities/capability-templates.test.ts` 在真的系统空间与项目空间里（本机实现、真命令、真沙箱、真的项目内核与语言服务；两个空间照产品的写法装在 `tests/support/spaces.ts`）
经真的门把**每个函数都跑一遍**，看它交回的是不是它说的样子、磁盘上是不是真改了——结果键取错一个、默认写法跑不通，类型检查看不出来，跑一遍就露出来。
这一轮核对就抓到两处：类型检查挡下了一段再普通不过的 `.map((symbol) => …)`（模版检查因此放开了 `noImplicitAny`），
实跑发现项目的 list 把 `.git/` 里的东西全列了出来（现在列举跳过版本库内部）。

**模版按需读、不常驻。** 它不嵌进声明、不进门的说明：随能力的模型面发布（`contract/surface.ts` 的 `template`），由当前会话的模块目录按授权提供。
模型拿不准怎么组合时通过 `velaros:system` 的 `modules.describe({module: 'velaros:project'})` 读取返回的 `template` 字段，输出后才进入上下文。
常驻模块的声明因此小了一半（`velaros:files` 8478 → 4402 字符，`velaros:project` 13252 → 8492）。
模版里也不教导出这种基本操作：怎么交出结果写在门的规矩里，一处就够。

### 导出照 ES 模块

`export default` 与具名导出都行，不强制 default：只有 `export default` 就交它；有具名导出就交 `{ default?, ...具名 }`，跟 `import * as m` 同形。
回执是给模型读的文字，不是整份 JSON：导出的字符串原样交回（多行照原样、不转义——代码、日志、文件片段本来就是这个样子），别的值按 JSON；
有具名导出时按名字分段；日志、系统插手过的地方、已经做完与停下时还没落定的调用各成一段；没跑完时第一行说失败码、行号与为什么。
`export default` 不中断执行。顺带查出一个老 bug：运行时报错的行号一直差 3——
包装改了两行、换算还减 1，而运行时行号从没被测过。现在偏移在隔离进程启动时量出来。

### 能力不折叠

能力交回的东西落在程序的变量里、不进上下文，所以能力不替模型决定看多少：`velaros:files` 与 `velaros:project` 的 read 交回要的整段（不给 range 就是整个文件），
`velaros:project` 的 list 交回全部条目（不给 depth 就是整棵树）、search 交回全部命中和它们所在的行（每个命中的文件一段命中处的连续正文）、
edit 与 inspect 交回完整差量，`velaros:code` 不按条数截，`velaros:shell` 与 `velaros:sandbox` 的 run 交回整份输出。
续读、游标、每页几条、结果预算、差量截断这些都删了——它们是工具时代的补丁，存在只因为回执要整个进上下文。
看多少、筛什么由模型在程序里定（先看大小，再切、再筛、再导出），门的规矩里写着这一条，模版里有「命中很多时先在程序里汇总」的写法。

剩下的只有**守内存的上限**，每个都在常量表里标明「只为守住内存」，写进声明，两边的数一致由验收核对：一次 read 交回的正文、一次 list 的条目、
一次 search 的命中、一次代码查询的条数、命令输出的字符数。超了不交回一部分冒充全部——读、列、搜整个失败（`SCOPE_VIOLATION`，message 说怎么收窄），
批量读里装不下的那个文件进 issues；命令输出是流，超了只留末尾并标 `truncated`。内核里原来按文件截命中（ripgrep 每个文件 400 处、回退扫描每个文件 120 处）的上限也拿掉了，
不然「全部命中」底下还是悄悄折叠。门的回执自己另有上限（导出的值、日志），那是交给模型的量，由程序决定导出什么，不是能力交给程序的量。

## 能力按注入装配，不绑死在空间上

**命名空间按能力起名，不按空间起名**。模型那边一件能力一个模块：

| `velaros:project` | read / list / search / edit / inspect / undo | — | ✓ 受项目治理的文件 | `@velaros-ai/velaros` 的 `project/` |

| `velaros:web` | search / read：搜索引擎搜、把网页读成文字 | 宿主给了不显示的页面时挂 | 宿主给了不显示的页面时挂 | `@velaros-ai/velaros` 的 `web/`（页面脚本、跳转链接解开、结果整理与正文切分；浏览器由宿主给） |
| `velaros:sessions` | list / ask / tell：同一个对话里的会话之间交活、等回答、捎话 | ✓ | ✓ | `@velaros-ai/velaros` 的 `sessions/`（模型面与入参核对；会话、排队、互相等待都在宿主那里） |

**一件能力只有一份实现、一份声明、一份代码模版**，不认识任何空间。空间之间不一样的地方全落在**注入的端口**上：

| 能力 | 端口 | 空间要回答的问题 |
| --- | --- | --- |
| `velaros:files` | `FileSpacePort` | `locate`：路径怎么解析、越界算不算；`commit`：怎么落盘（写或删，核对原字节）。本机实现 `createLocalFilePort` |
| `velaros:images` | `ImageSpacePort` | `locate`：能看哪儿的图；`resizeImage`：宿主会不会裁图缩图。本机实现 `createLocalImagePort`，项目里是 `projectCapabilityPorts.images` |
| `velaros:shell` | `ShellSpacePort` | `resolveCwd`：命令在哪儿跑；`commandPolicy`：危险命令的确认文案与风险分类；跑命令、列任务、刷新环境、停任务交给哪个宿主（`ShellHostPort`，本机实现 `createLocalShellHost`；项目里是 `projectCapabilityPorts.shell`，多一道项目资源门） |
| `velaros:sandbox` | `SandboxSurfacePort` | `resolveSource`：能镜像哪些目录；其余交给宿主的沙箱（`RehearsalSandboxHostPort`，含在镜像里跑命令；本机实现 `createLocalSandboxHost`，项目里是 `projectCapabilityPorts.sandbox`） |
| `velaros:computer` | `ComputerSpacePort` | 桌面控制交给哪份运行时：宿主把 `createComputerRuntime` 造的那份直接交进来（结构上满足端口）；没有桌面的宿主不挂这件能力 |
| `velaros:memory` | `MemoryScopePort` | 这个会话落在哪个作用域：宿主用 `createMemoryStore({ root }).scope(作用域)` 取一份交进来，作用域字符串由产品定、记忆不解释；会话开场的索引也由宿主用同一份的 `renderIndex()` 放进系统提示词（ADR 0010） |
| `velaros:office` | `OfficeSpacePort` | `getRootPath`：文档读写落在哪个根里（出了根一律拒绝）；`inspectEnvironment`、`runCommand`：本机有没有 LibreOffice、LaTeX 编译器，外部命令交给谁跑（只收原生 argv）；`locateMarkItDown`：按宿主自己的插件状态回答 MarkItDown 装没装、停没停用 |
| `velaros:browser`、`velaros:devtools`、`velaros:cdp` | `BrowserSpacePort` | 已经绑好会话与站点的浏览器：宿主拿 Electron 运行时按会话与站点拼它（要登录墙门控就用 `createBrowserLoginGate` 包一层）；站点工作区在哪由它的 `getContext` 回答，浏览器空间另外挂站点工作区上的 `velaros:files` |
| `velaros:web` | `WebSpacePort` | `openPage`：开一个用户看不到的页面（不落盘的临时会话、关掉后台节流）；`searchEngine`：用户选的搜索引擎；可选的 `resolveRedirect`：把 Google 的 `/goto` 跳转链接问一次换成真实地址 |
| `velaros:sessions` | `SessionsSpacePort` | 已经绑在发问会话上：`list` 这个对话里有谁，`ask` 交活并等对方这一轮跑完（开新会话、排队、拒绝互相等待都由宿主做），`tell` 捎话不等 |

**真正是两件事的不硬合。** 本机文件与项目文件看上去都是「读写文件」，其实不是一件事：项目里的文件有项目那一套——
校验器、带版本防护的事务、撤销账本、改完过校验才落盘；本机上的文件没有这些，
要的是路径哪儿都能到、写是原子的、改错了能整次撤回。硬合成一套，就得让系统空间在本机根目录上跑一个项目内核，
把项目的规则一条条关掉，还把 TypeScript 编译器拖进系统空间——一边为另一边的规则买单。所以是两件能力：`velaros:files` 给系统空间，
`velaros:project` 给项目空间，各有各的声明、模版与实现。两边在「怎么读、怎么改」上仍然一致（ADR 0023）：读出来都是一段连续的正文带第一行的行号，改的时候按路径写——`write` 整份写、`replace` 把唯一的一段原文换掉，同一个文件接连几步时后一步按前一步改完的算。
看图对两边是同一件事，所以拆成单独的 `velaros:images`，两个空间挂同一份。

**空间就是一张装配表**：给哪几件能力、每件能力用哪个端口、哪几件常驻。**装空间是产品的事**（ADR 0013），仓库里只有端口：
系统空间用各单元 `./local` 入口里的本机实现——路径可以是本机任意位置、`~` 展开到家目录（本机 shell 宿主的 `resolvePath`），
写是逐个原子替换，命令在本机任意目录跑，沙箱能镜像任意目录。项目空间挂上两件项目独有的能力（`@velaros-ai/velaros/project`），
共用能力的项目端口取自同一个单元的 `projectCapabilityPorts`：命令的工作目录钳在项目内、前台命令进项目资源门排队；
沙箱只镜像项目内的目录；看图只看项目里的图。

**能力单元是普通的目录，按同一套规范放在一起。** 模型 import 的每一件都在 `packages/velaros/` 下——跨空间注入的 files、images、shell、sandbox、memory，宿主装了插件才挂的 computer，
和项目独有的 project、code——一件一个目录，目录名就是模块名（`velaros:files` ⇄ `packages/velaros/files/`）；它们合成一个包 `@velaros-ai/velaros`，
构建配置只有包根那一份，单元目录里不再各抄一遍（包里不带许可证文件，仓根的 LICENSE 是唯一一份）；说明是每个单元根目录一份 `README.md`，包根的 README 只做索引（[模块 README 规范](../architecture/module-readme.md)）。每个单元目录的样子一样：`README.md`、入口 `index.ts` 与 `contracts.ts`、
`contract/ types/ impl/ utils/` 四个目录、代码模版 `template.js`、`spec/`（不变量登记与验收）与 `test/`。宿主按 `@velaros-ai/velaros/<单元>` 引用。
项目独有的两件长在项目内核上：问代码要用内核的符号表与读取，所以 `velaros:project` 与 `velaros:code` 同住 `packages/velaros/project/`，内核也在那里——
它就是项目那套规矩（事务、校验、撤销）的实现。**装配不在仓库里，实现都在能力里**：端口的本机实现跟着它实现的那件能力走
（本机 shell 宿主与受约束执行器在 `shell/local`，演练沙箱在 `sandbox/local`，本机文件与全局搜索在 `files/local`，本机看图在 `images/local`），
渲染进程能加载的根入口因此不掺 Node。工具经空间端口（`ProjectSpacePort`）向空间要项目根、内核与代码查询；
项目的宿主端口 `ProjectHostPort` 在它之上再加命令、沙箱与缩图，那是给共用能力装端口用的。

判据和上一节是同一条：**所有空间都一样的事在能力里只做一份**（有界读、认编码、核版本、留原文、压图、一批的成败、
命令分类、危险命令确认、钳上限），**只有空间真不一样的才进端口**。端口方法宁少勿多：要加钩子，等空间真要接的时候再加，不提前猜。

**只在危险命令上问人，没有权限与脱敏（ADR 0009）。** 读写文件、改生成物、写 `.git`、落回沙箱、跑会改东西的命令都不问；
读出来、命令打出来的都是原文，不遮像密钥的片段。这些闸拦不住任何事——同样的读写 shell 不经确认就能做——
只会让模型读到 `[REDACTED]` 改不了文件、改生成物被拒、每一步等人点头。留下的只有危险命令（递归删除、丢未提交改动的 git、
提权、格式化这类）的确认：它挡的是模型自己手滑造成的大面积不可逆破坏，2026-09-15 整仓被删就是这种。空间边界（项目空间出不了项目根）照旧，
它说的是「这个空间管哪儿」，不是权限。

模型那边：共用能力的声明是空间中立的，说明里不写「系统空间怎样、项目空间怎样」，只写「由当前空间决定」；
代码模版用相对路径，在哪个空间照抄都能跑。空间的差别由环境报告（根目录在哪）和端口的报错（为什么被拒）说清楚。

程序里看得见的只有返回值、`error.code` 与 `error.message`——工具时代那套 `cause.details`、`context.applied`、
`suggestedNextAction` 模型根本拿不到，所以要让模型知道的都写进 message，要让程序能分支的都给成专属错误码
（`FILES_EDIT_UNRESOLVED`、`FILES_EDIT_DENIED`、`FILES_UNDO_CONFLICT`、`SANDBOX_CONFLICT`、`SANDBOX_CHANGED`、`SHELL_UNAVAILABLE`；
项目那边直接用 `ProjectErrorCodes` 的原因码，候选、诊断、第几步第几处与下一步都写进 message）。

## schema 这一层直接消失

你问「为什么不把校验写进函数里，schema 全部消失」。**对，而且仓库里早有先例**：
`SystemFileOperations.edit` 第一行就是 `if (!isArray(input.files)) throw new AppError('VALIDATION', …)`，
`clampTextRange` 把 offset/end 钳进 `[0, length]`——这两处本来就是「函数自己拦」的写法，
zod 是盖在上面的第二层。

三条判断：

1. **校验属于那件能力自己**。它本来就要拦路径不存在、文件太大、编码认不出，顺手把形状也看了。
   盖在调用方那一侧的东西**换个入口就漏**——`run` 的 timeoutMs 与 maxOutputChars 一度只有 schema 在拦，
   绕开它直接调方法就没有上限。这不是推演，是实测到的洞。
2. **代码面这一侧现在没有 schema**。操作表就是 `名字 → 函数`，端口只负责登记、转发、整形错误。
3. **旧工具面的 zod 删不掉**：它经 `z.toJSONSchema` 发给 provider，那是**那边模型看到的参数表**。
   它的身份从「校验器」改回「旧面的参数声明」，随旧面一起退休。

**装饰器先不上。** 真去数剩下的重复：上限已经归位到操作自己，文件批量有 `utils/file-batch.ts`，
坏值大多会自然失败——补的只是 read/view 各一行 `isArray` 守卫（照 edit 早就有的那句写）。
两行不值得引入仓库里的第一个装饰器；等真出现大量重复再上，判据就是这一段。

## 注释写什么、不写什么

判据不是品味，是一个能执行的测试：**「字段名 + 类型」能不能推出它的含义和用法？能，就不写。**

**不写**：`path: string`、`command: string`、`timeoutMs`（名字里已经带了单位）、
「可选」（`?` 已经说了）、把字段名翻译一遍的话。

**要写，只写这四类**：

1. **缺省行为**——不传会怎样。「不传用宿主给的默认目录。」
2. **条件语义**——什么时候才有、才有意义。「`hasMore` 时把 `range.end` 当下一次的 `offset`。」
3. **跨字段约束**——和谁对应、和谁互斥。「`files` 与入参的 `files` 一一对应。」
4. **名字里没带的边界**。「一批最多 20 项。」

**一句话说完**。说不完的是设计有问题，不是注释不够长——那种情况该改形状，不该加字。

分节注释（`// ── …… ──`）是给读源码的人用的，**不进模型面**，生成器要滤掉。

## 能力怎么给：常驻、目录、按需读

**分三档**，理由在下面那条「为什么不许猜着写」：

| 档 | 给什么 | 谁在这一档 |
| --- | --- | --- |
| **常驻** | 完整声明与用法示例，附在运行说明末尾（系统提示，会话内不变） | 标准库 `velaros`；宿主 `residentModules` 列出的、每轮都会用的几个 |
| **目录** | 模块名、简介与操作名，程序查了才进上下文 | 其余授权模块，包括**用户 mod 注入的**：`velaros:system` 的 `modules.list`、`modules.search` |
| **按需读** | 完整声明、用法示例与每个操作的说明 | 模型拿不准时用 `modules.describe({ module })` 读，输出后进上下文，和别的执行结果一样按租约保留 |

**目录只说存在性，不说类型。** 一百个方法一两千字符——立项时光 browser 32 个工具的说明就 14,153 字。

### import 什么，就按什么的真实声明检查

`import` 不换回签名；检查器按本次授权取被 import 模块的真实声明：

| 程序里的情况 | 怎么处理 |
| --- | --- |
| 只 import 授权的模块 | 按它们的真实声明检查，过了就跑；没读过声明也一样 |
| 字段、属性或导出名写错 | **不执行**；诊断接上这个类型或模块实际有什么（script INV-38） |
| import 了没授权、没挂载的模块 | **不执行**，回 `NEEDS_MODULES` 与缺的模块名 |

**检查器只加载本次 import 到的那几份声明，不加载全量。**

**为什么不许猜着写**（这条一开始想反了，记下来免得再反一次）：
代码面里写错一处的代价**不是一次调用失败，是整段程序不执行**——中间一句猜错字段名，
前面写对的十行一起白费。所以「猜着写、让诊断教它」在代码面比在工具面**更贵**。
更糟的一种：猜出来的调用**恰好过了 typecheck 但语义是错的**（漏了必填默认值、用错枚举档），
那就不是白跑一轮，是真的做错事。

现在它落在两处：运行说明要求拿不准就先 `describe`，常驻档把每轮都用的那几个直接给全；
真写错了名字，诊断当场列出实际有什么，下一轮照着改，不必再猜。

### 回收靠结果租约，不写在 import 上

早先设想过写在 import 上的租约（`import … from 'velaros:git' with { lease: 'once' | 'task' | 'done' }`，宿主按预算与 LRU 回收导入过的声明），没有实现。
现在声明不因 import 留在会话里，也就没有要回收的声明：

- 常驻档随系统提示固定，会话内逐字不变，一直命中前缀缓存；它每次请求都计入预算，所以只放每轮都用的。
- `describe` 读到的声明是一次 execute 的输出，和别的结果一样按 `retain` 自动展示（1–32 个业务回合或 `'task'`，主任务默认 2）：
  到期换成引用卡，原文用 `memory.read` 召回；要留久一点用 `memory.retain`，用完了用 `memory.release` 提前退掉（[结果租约](../architecture/script-context-leases.md)）。
- 声明退出上下文不影响程序过检查：检查器每次按授权取真实声明，不看模型眼前还有没有那一份。

### 和工具空间分页差在哪

旧的工具空间分页是**能力闸**：没换进来就调不了，而且**运行期**才发现。
这一套是**编译期闸**：没授权的模块、写错的名字都过不了检查，**在执行之前拦住**，副作用一个都没发生，
而且报错直接给出实际有什么。差别是拦在哪一侧。

另一个白捡的性质：用到才付——非常驻的声明只在 `describe` 时付一次字数，常驻的那几份一直在缓存里。

### 还没定的

哪几个模块该常驻是**可测的经验问题**：同一批任务比「只给目录」与「常驻」的首次通过率和花费，再定 `residentModules` 放哪几个。
现在凭推演定详略是拍脑袋。

## 脚本时间线（已删除）

2026-09-18 按用户逐条定下的要求实现过：一次调用写、存、跑好几步，脚本库按相对路径互相 import，工作区只存哈希标记、不存文件内容，
按记录重放到最新。2026-09-20 随 `packages/code-surface` 整包删除（342be1f2），实现与细节见 Git 历史。现在对应的东西：

- **程序版本**：每次 observe、execute 的源码都自动存成不可变版本（`sourceRef`），检查没过的存成草稿（`draftRef`），增量编辑以它们为底稿
  （[增量编辑](../architecture/script-incremental-edit.md)）；`memory.list({ kind: 'programs' })` 列目录，`memory.read` 读原文。
- **执行记录**：请求、模型原文、脚本版本、Kernel 回执与下一帧，由 `session.trace(turnId)` 按同一存储里的真实记录串起来；宿主画脚本卡用 `runtime.trace` 分页读。
- **没有的**：跨会话的脚本库、按记录重放、工作区哈希标记。恢复不重放脚本：已派发操作的效果按 Kernel journal 与领域核对器确认（[运行主链](../architecture/platform-runtime.md)「恢复与边界」）。

**状态不跨轮**这条照旧：每段脚本一个独立的执行环境，跑完即毁；跨轮留下的只有源码版本与落盘的数据。
跨轮活着的变量会带来一类故障——**模型相信的状态 ≠ 实际的状态**：压缩一次之后它不记得变量里是什么，按二十轮前的印象去用，
程序能跑、能过检查、结果是错的。

## 六处设计漏洞（接进 agent 之前要补的四条）

### ① `for` 循环把事务拆碎了（**先前的判断错了一半**）

说过「批量字段是协议逼出来的，代码面里变成 `for`」。**对一半。** `files[]` 有一半是为省往返，
另一半是规矩 3 自己写的：**一次事务、全成或全不成、一个撤销句柄**。而模型写
`for (const f of files) await edit({ files: [{ path: f, … }] })` →
**一百个事务、一百个撤销句柄，中途失败留下改了一半的项目。**

**带事务语义的能力必须保留批量形状**，说明要明写「一次调用改多个，不要循环」。
代码面不但没消灭批量参数，反而要**更明确地**要求它——以前模型写不出那个错误的循环，现在能了。

**但不要为它单开一张登记表加一道门**（我做过一版，你否了，判断是对的）：那是仪式。
话写进方法说明就够了，而且**只写在真有事务的那个方法上**——`read` / `view` 的入参本来就是
`files: [...]`，类型自己说清楚了，再补一句「可以传多个」是废话；`edit` 才需要说，
因为「整批一次事务、一个撤销点」是类型看不出来的事实。措辞也要正面：
**优先用批量事务**，而不是「不要写循环」——告诉它该怎么做，别告诉它别怎么做。

### ② 审批拆成模块、先拿 grant 再动手（**作废，ADR 0009**）

原来的设想是写之前先 `requestWrite` 拿一张窄的 grant，免得循环里弹一百次确认。2026-09-18 写不再问人（ADR 0009），
这件事的前提没了：`velaros:approval` 模块、grant 登记表与逐次校验都不建。只剩危险命令逐条确认——它挡的是一次手滑的大面积破坏，
本来就该每条都问，不做成 grant。

### ③ 中止或失败时，模型不知道自己做到哪了（**已实现**，INV-16）

工具面里中断落在两次调用**之间**，天然干净；程序里落在执行中途，**副作用是真的**。
现在只回 `{failed: ABORTED}`。

这推翻先前一个决定：说过「不回放调用清单，模型自己知道它写了什么」——**成功时对，失败时错得离谱**。
**失败与中止时必须逐条列出已经完成了哪几次调用。**

**通用事务做不了，别假装能做。** 跑过的命令回滚不了；`edit` 能做事务是因为它的副作用在我们手里。
包一层 `transaction()` 会让模型以为失败了就没事发生。能做的是**账**：它不承诺回滚，承诺**知道**。

落地形态：`CodeProgramResult.completed`，**只在没跑完时给**（跑完了模型自己知道调了什么）。
每条是 `{call, ok}`，连着的同名同结果折成一条带 `times`——账上只记「调的是谁」不记参数（参数可以很大），
所以循环里那几笔本来就分不开，折成一个数不丢信息，却让「读了 23 个文件之后停在这」一眼看得出来。
账超过 60 条时保留结尾并在 `notices` 里说明：中断现场在尾部。

### ④ 能力调用被计进超时（**已实现**，INV-18、INV-26）

程序停在 `await` 上等用户点确认，而超时在走。用户去倒杯水回来——程序被我们自己杀了，而他刚点了同意。
等命令也一样：`run({ command: 'npm test', timeoutMs: 600000 })` 声明里许了十分钟，程序的墙钟却只有三十秒。
**墙钟只管程序自己的计算，能力调用的时间一律不算**——命令跑多久由它自己的时限管，等用户点头也在调用里。

落地形态是一把**时钟闸**：运行器把 `holdClock` 递给分发回调，调一次停表，调它返回的函数恢复。
停的是「还剩多久」而不是「什么时候到点」——等完按剩下的预算接着走，用户想多久就多久，程序自己的预算一点不变。

要点在于**必须在等待开始时停，不能等结束后把时间补回去**：补时间的写法里，程序在用户还没点之前
就已经被杀了，那笔时间根本没机会补。第一版差点写成补时间的样子。

谁来停？**会话在每次能力调用开始时停、落定时恢复**，端口不必管。第一版只给 `velaros:approval` 停、别的能力「内联问人时拿 `holdClock` 自己停」，
结果端口那一侧根本收不到这个闸（`CapabilityOperationPort` 把它丢了），危险命令等确认、长命令照样被按超时杀掉——所以改成一律停。
代价是一个边界：程序发出调用却不 await、自己死循环时，循环要多跑到那次调用落定才被掐断，上界是那次调用自己的时限。

**程序停下时还没落定的调用要叫停，并告诉模型。** 超时、被中止、隔离进程崩了，或者发出去不 await 就交卷——那些调用没人等了。
会话给每一轮配一个自己的取消信号（外面停这一轮时跟着停），程序停下时触发它，把还在飞的调用逐条列进结果的 `unsettled`：
它们的副作用可能做了一半，模型要知道去核对哪几样。

### ⑤ 内存没有上限（观察项转必修，**已实现**，INV-17）

超时管得住 CPU，管不住内存。子进程按 `--max-old-space-size` 起（现 512MB）。

堆爆时 V8 是**直接 abort**：不抛异常、`done` 发不出来，光看退出码只会报成一句没信息的「意外退出」，
模型下一轮照样把整个仓库读进一个数组。所以要从 stderr 认出来，回 `TOO_LARGE` 并说清怎么改。
实现时踩到的两处，都值得记下来：

- **认 `close` 不认 `exit`**：`exit` 在进程退出那一刻就响，stderr 里的现场此时还没读完。
- **stderr 留头不留尾**，与日志相反：`FATAL ERROR` 那行后面跟着一长串 native stack，
  按尾巴截会把判据本身裁掉。第一版就栽在这里——测试报 `RUNNER_CRASHED` 才发现。
  顺带补上一个真 bug：`stderr` 配了 `pipe` 却没人读，管道填满会把子进程堵死。

### ⑥ 句柄没被 export 就泄漏（观察项）

`sandbox.create()` 的 `box.id` 没交出来，镜像就留在盘上没人管；后台任务同理。
宿主知道自己创建了什么，应该在 `notices` 里报出这一轮新建的句柄。

### ⑦ 出参没有运行期校验（观察项）

入参有 schema 校验，**出参从来没有**。今天不要紧（模型看不见出参类型）；
代码面里它**整个程序都建立在出参类型上**，宿主实现与声明一漂，程序会在莫名其妙的地方炸。
开发期该按声明校验一次回执，把漂移抓在自己人这边。

## 一条推论：mod 的成本结构变了（记一笔，未开工）

模块形态之后，「万物皆 mod」从愿景变成了有路可走的事。变的不是「能不能装」，是**成本结构**：

| | 今天的工具面 | 代码面 |
| --- | --- | --- |
| 装一个没用到的 mod | 它的工具定义**每轮都在**，所以才需要分页机制去管 | 不常驻就不进请求，`modules.list` 查到时是一行，用到才付全量 |
| 装 20 个 mod | 每轮都在交税 | **边际成本接近零** |
| mod 作者要写什么 | 工具定义 + schema + 一堆散文说明，而且会漂 | **写 TS 类型与注释，声明是生成的**，漂不了 |

还有一条比省钱更要紧：**mod 之间能组合了**。今天模型没法把 `git.log()` 的结果直接喂给
`project.edit()`——中间要过往返、要进上下文。程序里就是三行。
**mod 从一堆孤立的按钮变成一个库。**

### 四件还没有的（别当已经成了）

1. **mod 的声明谁生成。** 我们的生成器是构建期跑仓内源码的；第三方 mod 得**自己把 `.d.ts`
   与目录条目打进包里**。这是对 mod 打包格式的硬要求，现在没有。
2. **声明是 mod 的自述，没人验证它说真话。** 声明写 `read(): string` 而实际返回 number，
   程序照样过检查、运行期才炸。今天的工具面同病——**不比现在坏，但别以为类型化就消灭了它**。
3. **命名空间冲突**：两个 mod 都想叫 `velaros:git`。要有登记与定名规则。
4. **mod 的操作仍要有宿主端口实现**，这块和今天一样多。

第 1、2 条要等代码面真跑起来才有实测依据，现在推演不准。记在这里是为了**mod 打包格式开工之前先看见它们**。

### 一条界线：`velaros:program` 要一直小

有人会想把 `sandbox` 这类「通用能力」也塞进 `velaros:program`。**不行。**
界线不是「通不通用」，是**有没有宿主端口、有没有审批、有没有副作用**：

- `velaros:program` 里是**这次运行自带的数据**（`input` 是本次参数，`blobs` 是宿主随这次提交附上的字符串），
  没有端口、没有审批、碰不到任何东西——所以它恒常授权、不占名额。
- `sandbox` 是真能力：建镜像要写盘，`apply` 会改真实目录，镜像里跑的危险命令照样要人确认。
  塞进 `velaros:program` 等于让它恒常授权、绕过授权账，**正好在最该拦的地方把闸拆了**。

`velaros:program` 长大的那天，就是这条界线被磨掉的那天。

**文字放哪**（按前缀缓存定，完整的请求布局见 [长程上下文](../architecture/long-running-context.md)「请求布局」）：

| 内容 | 放哪 | 为什么 |
| --- | --- | --- |
| 写脚本的规矩、`velaros` 标准库声明、常驻模块的完整声明与用法示例、宿主指令 | 系统提示（运行说明），会话内不变 | 逐字稳定，一直命中前缀缓存 |

**回执的形状**：导出与 `output` 交回给模型读的文字（见「导出照 ES 模块」与 [声明式观察输出](../architecture/script-output-observation.md)），图走结果旁边的附件通道；
没跑完时逐条列出已落定与没落定的调用（「六处设计漏洞」③④）。

**宿主要接的**见 [运行主链](../architecture/platform-runtime.md)「宿主配置」与 `packages/velaros/act/runtime/README.md`。和能力面有关的两条：

- 运行器：正式版不能用 `nodeSubprocessCodeRunner`（`NodeSubprocessRunnerIsReleaseReady` 恒为 false）。Electron 宿主用 `createSubprocessCodeRunner` 起自己的受信子进程，
  子进程里跑 `@velaros-ai/script/worker`；部署环境的隔离由宿主验收（`packages/script/README.md`）。
- 环境报告里写上空间的根目录（宿主的 `environment` 回调，每帧进 `runtime.environment`）：共用能力的声明说的是「由当前空间决定」。
