# 评测结构、结果与优化经验归档

日期：2026-10-07。用途：为后续运行时优化、验证设计和故障诊断保存可追溯的参考。

本次将历史评测整理为逐次结果、原始证据、请求账本、候选代码和经验清单。结论以原始验收、实际流程终态及用量记录为依据；同题复测用于诊断与回归，新一轮独立验证使用事前冻结的新任务。

## 最值得带入下一轮的结论

1. 标准 Node.js、Execa 和常用 npm 适合作为基础执行面；project 提供按需的事务编辑与写入前保护。能力是否被实际调用、最终交付质量和额外请求需要分别观察。
2. 成功必须同时满足产物验收和流程完成。最终回复、请求上限、取消、上下文阻塞及最后一次产物验证都影响交付状态。
3. 缓存以实际 SDK 请求体和供应商 usage 为依据。稳定的会话键、跨提交前缀和工具结果表示有直接证据；效率结论同时看请求、耗时、正确性和完整费用。
4. 大型代码迁移需要检验维护源文件到构建产物的传播、旧 API 兼容、干净重建及独立安装消费者。事务提交成功只是其中一个环节。
5. 评测存储需要归档与回收生命周期。累积轨迹的重复快照、重复候选和每次运行的完整依赖副本会持续占用磁盘。

## 失败经验与通用优化方向

| 触发 | 证据中的问题 | 通用改进方向 |
| --- | --- | --- |
| 原测试通过、新增 API 交付遗漏 | Commander 的旧 setter、accessor、不可重新配置属性和特殊键来源映射失败；同一来源问题可触发三项失败 | 用 API 合同和边界矩阵验证兼容性，按根因合并失败条目 |
| 源码迁移、生成发布文件 | fs-extra 命名导出模块被统一 default 处理后变成 undefined；维护源的实际实现未传播到 ESM 产物 | 检验模块导出拓扑、维护源传播、干净重建、重复构建与独立安装消费 |
| 写入后再构建 | 构建删除整个 lib 曾连原测试一起删除；最终测试保存需再次核对 | 按整个交付链检验副作用，对最终版本签发和再核验验证事实 |
| 产物已经通过、任务尚未交付 | 缓存试验服务目录组达到 18 次请求上限，缺最终回复；早期运行时存在相同分离 | 完成条件同时包含真实流程终态、独立产物验收及最终版本核对 |
| 上下文重组与材料读取 | 直接页、嵌套页和重组之间的覆盖证明曾不一致；历史 Flipt 案例保留待确认的 CONTEXT_REQUIRED 问题 | 核对不可变材料身份和实际覆盖，继续测试裁剪、跨会话、无签名、重置等反例 |
| 跨用户提交或工具结果表示变化 | ActLoop 重建引起前缀断开；断点迁移改变 Responses 工具回包表示 | 逐字比较实际请求前缀，保持系统、工具和结果表示稳定，按授权与容量变化更新历史 |
| 兼容端点与显式断点 | 实际端点返回 HTTP 400，提示断点不受支持 | 以端点实际能力声明和真实预检装配配置，分别记录显式断点与会话键 |
| 断流、错误与费用缺口 | 去重账本包括 301 条 HTTP 200 中断、21 条 HTTP 503，以及原有未知和 reserved 状态 | 保留原失败、请求身份、迟到结算与缺用量；按错误性质和限额管理重试 |
| 多层 trace 与工具计量 | 旧 pending 可覆盖终态；调用在不同页面重复出现；脚本、Kernel、原生工具属于不同层 | 以 session 和调用 ID 去重，保留层级、真实生命周期与冲突终态 |
| 空间耗尽 | 消融尝试因磁盘空间中断；临时根不断积累；进度日志重复整段轨迹 | 将准备、运行、归档校验和回收组成生命周期，对未完成尝试保留独立记录 |

## 下一轮优化顺序

| 优先级 | 目标 | 验证方式 |
| --- | --- | --- |
| P0 | 完成交付与最终产物一致 | 覆盖达到上限、断流恢复、取消、后续修改产物、源和生成物不同步等场景 |
| P0 | 用量、尝试身份和完整费用准确 | 检查失败请求、迟到 usage、重放、共享参照、多阶段及取消后的归账；未知值保留 |
| P1 | 默认执行面和按需能力的实际开销 | 固定模型、候选、任务与宿主工具，比较能力声明、实际调用、首轮执行、任务正确性和请求数 |
| P1 | 跨提交前缀及真实缓存收益 | 固定真实 wire 表示，交错运行多次，报告缓存读写覆盖、完整成本及耗时分布 |
| P1 | 上下文材料覆盖与维护效率 | 对直接、嵌套、重组、子任务和多会话路径做正反例及完整 Runtime 复现 |
| P1 | 最终构建与发布合同 | 新仓库、新模块形状、旧 API 边界、干净构建、独立消费者及含空格路径 |
| P2 | 分层耗时与资源生命周期 | 分开记录 SDK 等待、脚本、命令、排队和准备时间；长定向测试先确认真实执行状态 |

修复以通用机制为单位，建议与实际接口、能力边界及当前默认运行环境一致。任务名、仓库名与标准答案只用于证据定位。
