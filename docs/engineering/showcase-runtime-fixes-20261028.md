# 真实长任务运行修复差量

本轮只修改 Platform 拥有的 Runtime 和 Browser 能力，不改变 Desktop 配置或进程隔离边界。

## 真实故障与修复

- 回读提示在投影、历史差量及程序根对象三处附带 `rangeUnit: 'utf16'`，实际 `memory.read` 输入合同不接受此字段。删除提示中的无效字段；偏移仍按既有 UTF-16 合同解释。回归从真实归档提取提示，通过生成输入 Schema 并调用实际读取实现比对原文。
- Chromium 原生日期输入无法可靠通过全选及插入文本更新，原调用返回匹配成功但值不变。日期、时间、月份、周及本地日期时间通过对应页面 realm 的原生 value setter 设置，并派发 input/change；普通文本与 number 保持键盘路径。无效日期、只读及 disabled（含 fieldset 继承）不改值。最后重新定位目标，覆盖受控界面替换节点的情况。合成事件不带 isTrusted，模型说明已明确。
- Windows 真实整理支线被只读 Node 隔离边界拒绝，后续无有效补丁；最终错误却保留了早期已恢复的控制协议错误。现在已完成但无补丁时报告未提交及模型终态解释，不把解释包装为宿主验证结论。另一次整理因新用户输入取消，属于实际操作中断，不归为系统缺陷。
- 原生工具模型的交互维护默认改用生成合同的 list/read/submit 数据协议，不解释源码、不创建进程。仍使用原活动及祖先预算、读取授权、送达记账、ContextPatch 校验与原子发布。旧 ScriptAct 可以显式选择，原只读沙箱不放宽。
- Node 能力目录准备阶段补上独立时限、逐段取消检查及可取消文件写入，迟到租约仍回收；用户审批和运行期宿主等待的停表行为不变。已经过协议校验的空源码执行控制只准备 executions 能力及其包导出，仍通过原 Kernel 授权、身份与效果账本；普通业务程序保持既有能力目录。
- 执行追踪以持久作业状态保留 queued，不再把尚未取得普通槽的程序投影成 running。公开执行摘要增加 queued，Desktop/UI 消费端需同步展示排队。

## 合同与验收影响

`ContextMaintenanceOptions.execution` 是可选宿主配置，原生工具模型默认 data，其余保留 script。数据调用的 Schema 直接来自现有生成表面，只展开根引用以适配原生工具对象根约束。整份响应必须完整结束，名称、身份、顺序及所有参数先验证；任一参数错误整批不执行。读取正文到下一次完整模型响应才算送达，不能凭同响应的未见读取结果改变上下文。

Browser 宿主 `performTargetAction` 新增 `fill` action 和 value，返回可选 inputRequired 内部标记；自定义宿主需识别新 action。自带 Electron/CDP 共用页面实现。模型 `browser.fill` 签名未变，说明、生成表面、基线及 INV-25 已同步；不再承诺日期类输入事件是可信键盘事件。

## 验证记录

独立本地页面在 Windows 的外部 headless Chrome 上验证 10 类控件的替换、事件与清空，覆盖日期规范化、无效输入、禁用/只读、节点替换与同源 iframe。隐藏 Electron 的日期路径通过；该宿主测试环境的键盘输入未派发，因此没有用它声称普通输入成功，也没有加入未经证明的焦点修复。

维护回归使用真实存储、活动预算、生成 Schema 和发布实现，模型响应由测试控制，验证授权/越权、完整响应、整批参数错误、取消、保留收尾额度和超窗不发布；测试明确禁止打开 ScriptAct 会话。它证明 Windows 无 Node 的维护路径和边界，不替代真实模型的压缩后续跑。后者由 Desktop 消费发布快照后单独录制验收。

真实 Windows Node 四槽回归启动四个长驻程序，再提交第五个普通程序并确认 queued；随后控制进程停止一个目标，确认 cancelled 及排队程序执行产物。三次停止的目录准备、进程启动与 Kernel 操作分别为 487、1172、458 毫秒；五项相关排队与控制回归全部通过。控制进程先于目标进程组收束时允许一个终态唤醒帧，但断言仍只有普通、read、stop 三个作业，不能重复轮询。此结果只覆盖独立 Node 宿主，不等同 Electron 录制环境下的线程池/管道饥饿已经恢复；后续真实环境验证另记。

本地固定 Bun 1.3.13 的构建、顺序类型检查、lint、全仓格式、真实 tarball 宿主消费、所有权、37 项代码规范及模型合同检查通过。完整 Windows 测试在既有 Agent 的忽略取消驱动用例前持续无输出超过七分钟后中止，未标为通过。依赖安全探针通过，但 bun audit 查询遇到本机证书验证失败；DevTools bundle 的 Windows 再生成字节与已提交产物不同，这两个检查保留失败，未修改 TLS 或覆盖发布产物。正式 Linux 门禁必须验证全部项目。

Windows 的固定 Bun 1.3.13 不提供本地 HTTP 命名管道连接处理器，Script 子进程文件在该环境为 2 通过、13 跳过、2 个既有期望不符的失败（提前返回 UNAVAILABLE）；没有关闭保护。使用支持该连接处理器的本机 Bun 1.4.3 另行运行，8 通过、9 个 POSIX/兼容性跳过，新准备阶段三项回归实际执行。正式包与发布器仍固定 Bun 1.3.13，由 Linux 完整门禁验证受支持执行路径。

完整门禁及正式 Linux 发布结果在本轮发布记录中登记。Windows 不支持受限 Node 的既有路径仍可能导致依赖该能力的测试失败；不得跳过正式发布的完整检查或把该失败写成通过。

首轮 `v0.6.67` 的 Linux CI 与发布门禁在新增的审批/宿主等待计时测试失败；Runtime 的 1210 项测试通过，但整体验证不通过，未生成 Release 或发布资产，旧标签保持原提交。该测试的桥接客户端原先等待 TCP 连接关闭，而非 HTTP 响应完整结束，可能把连接回收时间错误计入程序执行；后续改用 HTTP 客户端读取完整响应，保留两秒传输超时、原程序限时和审批/等待断言，并使失败输出完整 outcome。修正进入 `v0.6.68`（Script 0.3.4），必须重新经过同一完整 Linux 门禁；不能以测试客户端调整代替发布验证。

后段 Linux 门禁诊断另发现原有 `qs` 6.16.0 固定覆盖命中 [GHSA-6pq8-jhm2-2vcw](https://github.com/advisories/GHSA-6pq8-jhm2-2vcw)。按上游修复升级至 6.16.1，只更新该项依赖解析；实际消费者闭包逐份验证带恶意 toString 的逗号数组、嵌套数组及无原型对象不会抛出异常，并保持普通序列化/解析语义。未忽略此公告，也未放宽安全门。
