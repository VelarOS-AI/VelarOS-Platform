# 独立反例调查原型（2026-10-14）

目前的真实证据支持执行流程存在缺口，尚不足以把差距归因于底层模型能力。双方已有配对使用相同模型；Runtime 仍暴露了长任务等待、期限反馈、语义验证和完整项目命令验收方面的问题。

## 已有证据与本轮假设

J1 的 Runtime 产物在原引擎语义对照中为 58/80，Codex 为 80/80。原 16 项功能检查与双方新增测试都通过；项目原有完整 Grunt 命令的覆盖率门禁则双方均失败，所以完整交付均未成立。追加 80 项只用于开发诊断，没有改写原冻结成绩。

给 v54、v56 独立审查同一真实坏产物及原任务后，两者都将相关兼容性条目判为通过，也都未调用可用的隔离验证工具。已有通用提示已经要求核对边界和旧行为；可选执行未能让这次裁定发现错误。另一个证据传递缺口是：后续审查只获得执行结果与源码哈希，没有收到实际执行的断言源码，难以审查断言本身。

本轮假设：先用有界执行调查具体反例，再用原材料和实际回执裁定，可能减少这类误判。多一次模型阶段会增加成本，必须与收益一起测量。

## main 上的实现与边界

`CompletionReviewOptions.counterexampleReview` 是可选宿主配置，默认关闭，启用时必须已有隔离验证宿主。仅在存在产物需求且当前快照没有问题时，先调查一至两项具体反例；必须实际尝试独立执行，调查意见不能直接充当事实证据。之后仍由现有需求裁定流程核对原文和回执。

调查与裁定共用原有模型、读取、执行、时间和取消边界；验证仍为最多两次、每次十五秒，没有增加模型执行权限。已执行结论要求绑定对应需求的当前版本有效回执，未知、取消、超时或清理不完整不能当作有效结论。实际断言源码与已有代码哈希一同送给后续裁定，使其能够检查测试是否合理。

公共变更限于可选宿主字段与评测配置透传；模型操作 schema 不变。README、不变量与差量报告已对应更新。并行裁定仍保持最多两个首次只读请求，来源引用保留在正确会话范围。
