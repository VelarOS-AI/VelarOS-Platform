## 已经实测的取舍

相同 ShellJS 新题、相同模型及预算下，完整交付三方均通过。旧 Runtime 为 240.855 秒、21 次请求、已知参考 $1.0647728；只保留末尾当前状态的 v62 为 269.583 秒、26 次、$2.9726992；Codex 为 143.846 秒、15 次、已知 $0.4370504，有一次用量缺失。运行顺序固定且每方一次观察，不能把全部时间差归于上下文修改。

旧版共 960,152 输入 token，其中 818,432 命中缓存；v62 为 855,859 输入，其中 165,888 命中缓存。v62 的全部 26 次请求均无历史状态帧；正式 SDK 离线复放逐项确认每次不可变历史仍是上次去掉末尾状态后的完整前缀。即使本地前缀保持一致，当前上游的实际缓存收益仍不足。

固定材料传输探针进一步区分了任务随机性：35,152 token 的完全相同请求重发时，34,944 命中缓存；随后两个保留稳定历史、更新末尾状态的请求，分别为 36,722/38,226 输入，仅各 6,272 命中缓存。显式缓存断点请求被上游以 `prompt_cache_breakpoint is not supported on this model` 拒绝。实验没有执行工具。它证明当前路由的可观察限制，尚不能定位上游内部缓存算法。

## 当前合同

1. **不可变事件与动态状态继续分工。** 用户消息、模型输出、调用和实际结果形成持久事件；当前任务、作业和材料状态由权威存储生成，完整审计保留原快照。
2. **在有限窗口内保留已接受请求。** 窗口内部沿用已验证的追加方式，给当前上游提供可复用前缀；所有历史状态明确保持原时间身份，末尾状态负责当前事实。
3. **以状态帧占用为独立重建条件。** 除现有总上下文容量外，单独核算重复状态的输入开销；达到预先确定的状态预算时，从不可变事件和完整当前状态重建一次。重建后的正文、引用、来源、租约、取消与执行身份全部重新核验。
4. **把取舍做成运行策略，而非任务特例。** 状态预算由上下文配置和真实输入计量决定，先用固定真实轨迹比较小窗口与大窗口，再确定默认值。评测以总请求、实际缓存和完整交付为准；不按 ShellJS、Commander 等题目增加专用提示。

本方案需要明确 Agent 请求保留与 Runtime 状态占用之间的合同，并扩展相应公开类型、版本、基线和验收。上游缓存配置保持已证实支持的能力；该改动不依赖修改第三方中转服务。

## 验收覆盖

先以已冻结真实轨迹进行零模型回放，核对每次历史/正文完整性、重建边界、最大状态占用和缓存前缀。然后覆盖长历史、并发执行、用户修订、材料失效、图片、取消、上下文维护及恢复的实际 Runtime 回归。

最后预先冻结另一个真实任务、旧版/新版/Codex 候选、顺序、完整交付判据与相同资源上限。记录全部失败和未知用量。只有功能与维护交付通过，并观察到可接受的时间和费用取舍，才选择新默认策略；失败实验作为后续判断证据保留。

长程任务另需完整 75 分钟生产性工作与 checkpoint 恢复验收。上下文窗口调整不能替代该实测，也不能自动解决模型遗漏兼容性边界或过早结束的问题。

## 实施记录

Agent 9.9.0 增加 `ActContextPolicy.retainedFrameRatio`。同一驱动对保留请求和移除插入帧的计量副本使用相同当前正文、工具、逻辑事件、不透明续接与校准；边际输入超过预算后重建权威投影并重新核对正文。计量不发送模型、不消费交付租约。最终发送门再次核对，`model-request.retention` 留下当前用量、预算和重建前用量。比例 0 表示逐轮重建，1 保持仅按总容量回收。

零模型回放以原始可见文本为口径排除加密续接，按事先设定的候选比例比较 1/8、1/4、1/3、1/2。实测前的实验候选选 1/8：三条开发轨迹的历史状态占比为 13.9%–19.4%，保留相邻前缀比例 80%–85%。首版回放把不透明密文也算进可见文本分母，原文件保留，付费登记前已修正口径。该回放不是缓存命中或账单预测。

候选本地验收与完整 QuickLRU 保留产物审计均完成。对照使用同一 v63 候选、模型和任务，仅改变比例（1 与 0.125），另运行 Codex。三方都通过 7/7 功能组、原 115 项回归，以及维护测试、类型、lint、文档、例子和真实回执审计。
