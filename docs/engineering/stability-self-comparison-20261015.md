## 复现与处理

### 验证范围与实际交付入口

当前版本的 p-filter 开发回归用时 176.471 秒、9 次物理请求，11 项功能验收通过，用量完整，冻结费率下参考费用为 $0.413212。新增 `test-d/partition.test-d.ts` 没有被配置中的默认 tsd 命令发现；在独立交付副本加入必失败类型断言后，默认命令仍通过，而显式指定该文件会失败。原始完整交付判断为失败。

r1 的通用指导要求先核对检查发现规则，以测试清单或临时必失败断言验证实际覆盖，并把检查对应到最终产物和消费入口。已有行为的边界指导适用于普通 Node 编程环境。这是模型工作指导；独立验收继续负责检查最终结果。

指导原文增加约 226 字符，固定夹具的前缀预算从 1,800 调整为 2,000 字符，文本协议提示总长预算从 2,600 调整为 3,000 字符；完整控制语义的 3,600 字符上限保持。实际请求、费用和交付变化共同记录。真实任务不因单项功能验收通过而自动认定完整交付。

### 请求预留额度与已执行请求上限脱节

首轮 p-filter 候选有 14 次物理请求、1 次缺失用量，已知参考费用 $0.5366512；EventEmitter 候选有 10 次物理请求、1 次缺失用量，已知参考费用 $0.3802488。两次运行均因预算准入停止。完整费用未知，终态失败。

首轮评测把单次限额设置为 $24，与预算器每次至少 $20 的保守预留不匹配；网关已把输出限制为 12,000 token，预留仍沿用旧上界。缺用量继续保留全部预留，因此后续请求无法准入。这既是本轮配置问题，也说明预留应绑定已执行的请求上限。该限额是评测配置，不是供应商扣费。

新账本冻结 `reservationOutputTokens`，网关在派发前保证实际输出上限不超过该值。输入仍按既有 1,050,000 token 最大边界、最贵输入费率与长上下文倍率保守预留；不把运行时的输入估算视为供应商硬边界。本轮预留为 $10.86。缺失用量继续未知并保留预留；已有账本不能改变这一合同后重开。

用首轮 p-filter 的原始用量离线重放，两个账本的已知费用与一笔未知用量完全一致；旧策略拒绝下一请求，新策略可准入。这是预算机制验证，不计作新的模型任务成功。后续自对照双方统一使用新账本、每次 $60 的预留限额及 80 次请求上限。

### 复制准入与取消

评分原先把整份工作区、冻结源、依赖和源码证据重复按完整目录预估。新逻辑使准入计量和实际复制共用排除规则，分别计入工作区、冻结依赖和原测试恢复；源码证据按真实 Git 差量、新文件及清单预留。复制支持文件系统克隆，取消检查覆盖计量、Git 证据采集和逐项复制。

评分仍使用独立产物副本，原始日志与工作区归档保持完整。大产物仍占用预算，空间不足时保留现场并停止后续步骤。该修复不能视为已经解决所有大数据评分空间需求。

### 原项目完整命令没有进入执行前检查

p-retry 的冻结环境安装了 TypeScript 7.0.2，而原项目的 typescript-eslint 不支持其 API。原准备流程只检查 AVA 回归，两版运行都在任务中更换了已安装 TypeScript，才得到 `npm test` 通过的回执。基线使用 5.9.3，候选使用 6；清单没有变化，但实际依赖版本发生变化，违反任务约束。在原冻结依赖下重放两份最终交付，完整命令都因相同的工具链错误退出，运行行为验收仍通过。

已扩展既有完整项目验证入口，支持 `maintainedValidation.npmScript`，由冻结 PATH 中的 npm 执行原脚本及生命周期钩子。准备阶段先通过同一完整命令，评分阶段再用冻结依赖和包含新增测试的交付副本执行。环境说明明确遵守任务的依赖版本约束。新增控制核对真实 pretest/test/posttest 顺序与错误传播。

用三个真实项目进行无模型调用的准备验证：p-filter 和 EventEmitter 完整入口通过；p-retry 在请求模型前被原工具链错误拒绝，现场归档。旧尝试的冻结文件与评分均保留。这是本轮评测环境缺陷及其修复，不能把它解释为候选能力提升。
