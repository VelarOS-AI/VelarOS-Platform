## 已确认的问题

当前 Context 在请求前累计 `reservedTokens`，供应商返回实际用量后只增加 `inputTokens`、`outputTokens`。准入采用 `max(累计预留, 累计实际) + 本次预留`。已知请求的预估余量持续占用预算；在另一种组合中，累计取最大值又不能完整覆盖已知实际与其他请求的未知预留。

L07 的子任务 `1f9a4746` 有 47 次真实模型请求，逐一按请求身份关联原始请求与响应：45 次提供用量，2 次缺失。全部数字与持久总账一致。

| 口径 | token |
| --- | ---: |
| 子任务配置上限 | 4,000,000 |
| 当前累计预留 | 3,970,562 |
| 供应商已报告用量 | 2,839,502 |
| 两次缺失用量对应的原始预留 | 206,795 |
| 已知实际加未知预留 | 3,046,297 |

后两种可用额度比较只证明计账差异，不能证明子任务因此一定完成。两个未知请求继续占用完整预留，也不能据此计算完整费用。原件：真实子任务核算（`archive/model-budget-settlement-review/long-child-accounting-audit.json`）。

该控制确认“过早耗尽”和“混合实际/未知时占位不足”均由当前算法产生。当前算法是现有接口合同，调整需要一起覆盖调用方与持久恢复。原件：生产 API 控制（`archive/model-budget-settlement-review/current-budget-controls.json`）。

## 建议合同

每次物理模型派发获得宿主管理的稳定预算请求身份，绑定逻辑任务、角色及所属祖先。预算状态记录单次预留、派发事实、已知用量及结算状态。同一请求的重试结算幂等；新的实际模型派发取得新身份并计一次调用。

准入使用：已结算请求的实际 token，加已派发但用量未知的预留，加尚未派发的活动预留，再加本次拟申请预留。调用次数独立计算。实际用量高于预估时完整记账并阻止后续超额派发；已消耗用量不能回滚。明确报告 0 属于已知用量。

确认未派发的请求可释放占位和调用计数。派发后的取消、断流及供应商缺失用量保持未知并保留占位；迟到用量依原请求身份结算。完成核查、搜索、整理和业务子任务使用同一流程，所有祖先各记一次。费用评测继续依供应商用量与独立价格口径报告，缺项保持未知。

小时窗口按请求的原始归属时刻登记预留，再按同一身份修正该桶。不能从当前桶扣掉另一个窗口的额度。跨节点结算失败保留待结算记录，可幂等重试；不能通过“先退回一次调用、再重预留实际用量”暂时放开并发预算。

旧任务以已持久化的保守总额作为迁移底座，既有未知计数保留。新账本只接管迁移后的请求；历史数据不足时不推测退款。任务身份隔离迟到回执，关闭和新任务启动不得使旧请求写入新任务额度。无需改动已有评测原件。

## 实施边界

1. Context 的持久任务预算结构与 `ContextViewSession` 增加带身份的预留、派发、结算入口；用 CAS 核对同一任务、并发上限、重复及冲突回执。旧聚合接口沿用保守兼容行为，正式 Runtime 切换到新接口。
2. Agent 主循环及 Runtime 的 `BudgetedModelDriver`、`ModelToolRuntime`、`ModelToolActivation`、CompletionReview、ContextMaintenance 统一携带预算身份。逐项核对上游重试、队列取消、迟到响应和跨祖先失败恢复。
3. 更新公开合同、类型、文档和使用方。Desktop 仍显示真实累计用量、未知请求和停止原因；任何展示不把预估当作账单。
4. 完成兼容与错误恢复验证后冻结新候选。未派发的评测可以重新冻结候选；已开始的对比保持原候选及预算，分别归档。
