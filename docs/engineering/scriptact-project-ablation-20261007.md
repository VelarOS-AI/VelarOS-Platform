# ScriptAct：project 与标准 Node 的真实仓库任务对比

日期：2026-10-07。完成六组主对比、两组移除宿主补丁命令的补充复测；另保留一次磁盘空间不足造成的中断记录。

**建议维持标准 Node.js、Execa 和常用 npm 为默认执行面，project 作为按需事务能力。** 本轮呈现质量与效率的取舍，没有证明某一方案稳定地全面胜出。project 确实阻止过错误内容写入；把全部编辑强制交给它，没有呈现一致的效率优势。业务语义、旧接口兼容和最终构建产物仍依赖独立验收。

## 任务与控制条件

使用两个真实开源仓库的冻结源码实施编程任务。它们都是此前用过的开发复测任务，并非首次未见任务，也不是统计意义上的多次重复试验。

| 任务 | 冻结源码 | 工作内容 | 独立验收与原始回归 |
| --- | --- | --- | --- |
| Commander | `tj/commander.js`，`395cf7145fe28122f5a69026b310e02df114f907` | 增加带来源的选项快照 API、泛型声明、文档、示例与测试，保持旧行为 | 9 项功能验收；原始 1365 项测试 |
| fs-extra | `jprichardson/node-fs-extra`，`1e223d3b1e26b7ebef7f402acf0e3b5533cc5833` | 将 29 个生产文件（28 个 JS 模块和一个 ESM 入口）迁移为维护中的原生 ESM，保持 CommonJS/ESM 接口、构建、发布与原测试 | 54 项功能验收；原始 745 项通过、8 项基线跳过 |

所有运行共用 Platform 提交 `a2a9e5ec508da222cf68079ea15d7831544eaf67` 的同一个冻结运行时：`runtime-0e8c9a7330ee`。候选包含 5,386 个文件；最后逐文件复查哈希一致。任务执行期间没有针对样本修改产品运行时。

固定模型为 `gpt-5.6-sol`、high，普通 request 生命周期；上下文 65,536、输入窗口 32,768、最大输出 12,000 tokens、每次任务最多 45 分钟、工具并发 4。每次运行使用独立工作目录与会话。任务、依赖、评分器及限制在付费请求前冻结；原始回归先通过，新功能验收先确认会拒绝未修改源码。

主对比包含三个条件，每个任务各运行一次：

- **不加载 project**：保留标准 Node 执行及共同的运行时控制能力。
- **按需提供 project**：只增加 `velaros:project` 和正式项目上下文来源，任务正文保持相同；代码查询、搜索和子任务能力均与上一组一致。
- **要求 project 编辑**：在第二种能力配置上，额外要求源码、测试、文档和配置编辑通过 project。读取、计算、构建、测试及构建生成物仍可使用普通 Node/Execa。这是单独的编辑策略干预。

模型请求数包含上下文整理请求。耗时从模型任务开始计至任务结束，包含模型执行的检查，不含后续独立评分。成本采用冻结的参考价格，不是供应商账单；`≥` 表示部分请求缺少用量，只能给出已知下限。

## 宿主工具审计与补充复测

完整程序审计发现，四个自由选择编辑方式的主对比运行都经 Execa 使用了宿主的 `apply_patch`。它实际指向 Codex 程序，不是 Node 内置 API，也不是产品默认 npm 依赖的一部分。主对比仍是同一宿主上的 project 能力对比，但不能用它直接证明只有产品默认标准工具时的效果。

因此额外做了两个单次复测：移除 PATH 中注入该辅助命令的目录，关闭 project，保持任务、模型、候选、依赖、评分器、限制和原始提示相同。真实运行时的零模型预检确认调用 `apply_patch` 得到 `ENOENT`，模块目录中没有 project。模型没有收到任何先前答案或隐藏验收反馈，也没有按结果选择重试。

这是 PATH 隔离，不是操作系统沙箱；普通宿主命令和项目已有 npm 依赖继续可用。要求 project 编辑的原运行没有使用 `apply_patch`，但没有重新在隔离 PATH 下配对重复，所以下表与上表的跨表比较属于补充观察。

| 任务 | 条件 | 功能验收 | 原始回归 | 模型请求 | 耗时 | 已知参考成本 |
| --- | --- | --- | --- | ---: | ---: | ---: |
| Commander | 不加载 project，移除宿主补丁命令 | 6/9 | 1365 通过 | 38 | 7.95 分钟 | ≥ $2.0561 |
| fs-extra | 不加载 project，移除宿主补丁命令 | 53/54 | 745 通过，8 跳过 | 57 | 9.96 分钟 | ≥ $2.9811 |

这两次复测中，模型在辅助命令不可用后改用 Node 文件 API。标准环境能够继续完成大部分工作，但两题都存在验收遗漏。不能将主对比里更快的结果直接外推为产品默认环境的稳定收益，也不能用这两次单样本复测证明辅助命令缺失必然造成分数下降。

## 静态审查与动态验证发现

### Commander：相同测试名下的失败原因也需要区分

主对比的三组都漏掉两个旧 setter 兼容性场景：可写但不可重新配置的属性，以及已有 accessor setter。静态检查确认，模型改动了旧 setter 的赋值方式；事务提交成功并不保证 API 语义兼容。

隔离复测保持了原 setter，但在新快照 API 中增加了来源映射的 own-property 限制，使特殊键 `__proto__` 的来源与既有 `getOptionValueSource()` 返回值不一致。**同一个来源投影问题触发三项失败，并不是三个独立缺陷。** 因而 6/9 与 7/9 的差值也不能直接解释为某种编辑工具具有稳定的语义正确率优势。

所有 Commander 运行都通过了原始 1365 项测试，但都没有完整通过新增合同验收。

### fs-extra：最终构建产物决定交付是否正确

- 不加载 project 的主对比运行通过了 54 项验收与原始回归；后续审计确认其修补阶段使用了宿主 `apply_patch`。
- 按需组只通过 47 项验收。它给每个生成模块统一追加 `module.exports = module.exports.default`，其中仅有命名导出的 `mkdirs/utils` 没有 default，导致发布后的模块导出变成 `undefined`。Promise、callback、同步操作及独立安装消费者失败；原始回归也在 180 秒后超时。超时后没有完整 Mocha 报告，不能把汇总中的零项计数当成“零失败”。
- 要求 project 编辑的组通过了 54 项验收和原始回归。期间也曾因构建脚本删除整个 `lib` 而删掉测试，之后模型恢复测试并修正构建。project 对编辑提交的保护没有覆盖任意后续构建进程的全部副作用。
- 隔离复测通过 53 项验收。其构建脚本从 `src/esm.js` 提取导出名称，再拼接对根入口的引用，未完整使用该文件的实际实现。因此修改这个维护源文件的行为不能完整传播到 `lib/esm.mjs`，违反源码作为构建事实来源的要求。

四份完成的 fs-extra 产物均逐个核对了 147 个原始测试和夹具文件，最终内容、类型与权限和基线一致。判断失败的是最终实现，不是通过改写原测试取得的假成功。

### project 的具体作用与边界

实际观察到：project 拒绝了一批 27 个文件的写入，因为生成的 ESM 导入别名存在语法错误；记录效果为 `none`，模型修正后重新提交。这是可确认的写入前保护。

同时，模型遇到了 102 文件事务超过 100 文件上限、空 steps 校验失败，以及编辑参数的执行前校验错误。请求和成本全部保留。已登记的模块调用数与所有尝试提交的程序数不是同一指标。

大迁移的额外请求还包含构建兼容修复、验证、上下文整理和供应商流清理异常，不能全部算成 project API 本身的开销。本轮没有做并发人工修改或撤回任务的受控对比，不能把这些合同能力当成已经测出的收益。

### 补充路径复现

静态检查发现 project 强制组的构建脚本将 URL 的 `.pathname` 当作普通文件路径传给 esbuild。对完成产物增加了相同的事后复现：普通目录和含空格目录分别构建，使用归档中的原依赖和相同 Node。

| 产物 | 普通路径 | 含空格路径 |
| --- | --- | --- |
| fs-extra 不加载 project | 通过 | 通过 |
| fs-extra 按需提供 project | 通过 | 通过 |
| fs-extra 要求 project 编辑 | 通过 | 失败 |
| fs-extra 隔离宿主补丁命令 | 通过 | 通过 |

这是冻结 54 项之外的诊断，单独记录，没有修改原评分。它再次说明，“54/54”只能代表已覆盖范围，语法核验也不能保证所有运行环境下的行为正确。

## 对架构的判断

1. **基础环境继续采用标准 Node、Execa 和熟悉的 npm。** 原生读取、搜索、计算、构建、测试和普通编辑都能直接执行；标准工具的实际可用性与版本要能查询。
2. **project 保留按需入口。** 在任务明确需要原子提交、写入前核验或撤回时使用其事务能力。这个组合兼顾熟悉的执行方式与自定义能力的具体价值；本轮没有给所有源码编辑增加强制 project 路径的充分证据。
3. **优先加强最终验收与事实核对。** 最终源码、重新构建的产物、旧接口行为和独立安装检查应形成一致证据。模型在中间步骤通过测试或最终宣称完成，都不能替代这一步。

若要决定是否更改默认策略，还应在冻结的未见任务上做多次配对，显式记录宿主命令环境，并覆盖真正需要事务保护的任务。本报告不以单次分数差宣称普遍优胜。

## 本轮代码差量与验证

改动只涉及评测入口与报告：

- `runtime-capabilities.mjs` 增加只提供 project 的能力档，以及单独的 project 编辑策略，避免同时改变代码查询、搜索和子任务能力。
