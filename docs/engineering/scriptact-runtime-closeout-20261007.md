# ScriptAct 运行环境与缓存收尾

日期：2026-10-07。开发基线：`a2a9e5ec508da222cf68079ea15d7831544eaf67`。

## 组织边界

基础执行环境为 Node.js ESM 与 Execa、diff、ripgrep、globby、yaml。标准操作直接使用原生接口；包的实际版本、清单、README 和类型入口按需查询。Skill 按会话装配说明、依赖和授权能力；project 由项目工作区提供事务能力。进程约束由宿主管理，业务正确性通过最终产物验收判断。

本次沿用已有 Skill、能力目录和验证账本，补齐实际执行环境发现、原生工具结果的缓存断点和最终验证版本核对。

## 差量与合同影响

| 所属模块 | 改动 | 原因与影响 |
| --- | --- | --- |
| script | `VELAROS_HOST_DIR/index.json.execution` 发布实际子进程的 Node 版本、执行文件、平台、架构、cwd 与有序 PATH | 与包目录在用户源码运行前一并发布；只记录这些环境事实，其他变量和凭据保持私有。目录是启动快照，命令按实际 PATH 解析 |
| act/runtime | 默认提示提供 execution 查询入口，并要求验证对应最终交付版本 | 固定系统前缀只包含环境约定和必要使用边界，完整 API 及 Skill 正文按需读取 |
| context | 成功完成前重新探测报告中 helper 签发的 current 证明 | 后续步骤改变产物或失去探测覆盖时阻止完成，报告该项为 unknown 并要求补验；原单项事实保持不变，新增探测独立记账 |
| model | 工具结果断点按 Responses / Chat 实际 SDK 落点转换 | Responses 使用 output 内容块；Chat 使用结果 part。结果文本和 JSON 编码正文保持原字节，显式输出断点计入共用额度 |
| kernel / agent | `ModelContextStatus.cache` 的两个分项分别可选；每次请求前清除旧摘要，只填实际报告的值 | 修正缓存写入未知被补成零、当前请求缺少缓存用量却继续显示旧请求数值的问题。消费方应将缺项视为未知；usage 事件与原费用口径保持 |
| long-tasks 评测 | 冻结 Node 二进制与命令 PATH，启动时核对并恢复 | prepare 最后一个可选参数为 command-path；默认使用准备时 PATH。运行控制器后来继承的 PATH 不影响冻结条件 |

模型通过标准 Node 和既有按需模块工作。context 的完成行为收紧为：报告成功且包含 helper 的 current 证明时，再核对一次这些证明；失效返回 `VERIFICATION_ARTIFACT_CHANGED`，继续补验。普通 Node 任务的验证由模型执行，宿主挂载领域验收器时才有这项机器核验保证。完整依赖覆盖、原子探测以及最终发布期间的写入协调仍由领域宿主提供。

## 提示词与缓存审查

通过完整 Runtime → Agent → Model → AI SDK 的两轮离线请求体测试，同时运行真实 Node 子进程，核对显式缓存启用与关闭两种配置：

- Node 基础说明、工具定义和会话缓存键在连续请求中保持稳定。
- 上次请求前缀逐字保留，动态环境状态在新帧尾部更新。
- 完整自定义声明按需查询；默认系统说明保持精简。
- 原生调用结果只进入对应工具回包，启用时断点到达结果正文；显式缓存关闭时继续保留会话键。
- 调用方已有工具输出断点占用共享额度，自动断点不超过剩余三个显式槽；内部标记不进入供应商请求体。
- 供应商报告的缓存读数如实交付，缺失的缓存写入量保持未知。

发现的断点缺陷是：原生工具回包携带了消息级内部断点，但 OpenAI 转换只选择 text part，工具结果无法成为实际缓存落点；工具 output 内的显式断点也没有参与额度统计。现在按实际 SDK 协议转换并统计。测试覆盖文本、JSON、显式点预算、禁用配置和原生多轮执行；Anthropic 的原有断点预算与 TTL 测试也通过。另补齐缓存摘要的未知语义，五轮测试覆盖只报读取、只报写入零、未报缓存和完全未报用量后的状态。

## 已有真实任务的缓存事实

重新核对[项目能力对比记录](scriptact-project-ablation-results-20261007.json)及对应的八份冻结配置：它们均显式设置 `openaiExplicitCacheBreakpoints: false`，继续使用会话缓存键。

| 范围 | 已知输入 tokens | 已知缓存读取 tokens | 已知输入中的缓存读取占比 |
| --- | ---: | ---: | ---: |
| 六组主实验及两组隔离复测 | 8,430,023 | 4,092,544 | 48.55% |

逐组占比为 44.06%–58.89%。共有八次请求缺少用量，上述比率只覆盖已知部分，也不包含中断尝试。它说明之前已经观察到隐式缓存命中；这次显式断点修复的线上增益仍需后续真实 usage 判断。缓存比例单独不能证明整体成本或任务质量更优。

`apply_patch` 的已确认事实仍是它从评测宿主 PATH 解析到了外部命令。模型训练习惯或代理服务封装都可能影响调用倾向，调用倾向不足以确认 API 后端身份。产品以实际环境和能力发现为依据；冻结 PATH 记录的是评测条件，不是 OS 沙箱或外部命令完整性证明。
