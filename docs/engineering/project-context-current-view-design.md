# Project 当前文件视图与历史快照

状态：已实现，候选版本 Agent 0.6.26、Project 2.0.22。Workbench 与 Desktop 已接入；验收使用独立 worktree 内安装的候选包。结果见 [验收记录](./project-context-current-view-acceptance.md)。

## 设计判断

自动维护文件上下文是可行的，关键在于分开保存执行事实、当前文件状态和模型发送视图。直接在持久历史里替换旧源码会破坏审计和旧版本召回；仅保存最新 revision 又不足以让模型知道修改后的内容。因此由框架管理源码版本和注入，模型继续使用原有读、编辑、写入、回滚与召回工具。

实现时重点处理了以下问题：

- 延迟返回的旧读取不能覆盖已经更新的当前状态，异步归档期间发生的修改也需要条件更新。
- 事务提交后的归档故障与磁盘修改结果分别报告，避免模型误以为没有写入而重复执行。
- 提交内容从内核最终补丁取得，外部程序立即改写磁盘时，仍能准确保存中间提交版本。
- 归档全文必须经过读取授权与脱敏；召回还要检查当前权限。子 Agent 的来源访问受自身工具范围限制。
- 相同正文按内容去重，调用来源另存轻量记录，保证不同分支在历史折叠、重启后仍能恢复各自阅读范围。
- 正文窗口、完整档案和请求预算分别管理，防止大量编辑导致上下文无限增长。

## 数据与代码所有权

| 模块 | 责任 |
| --- | --- |
| Agent `agent/context/resources/contracts.ts` | 文件身份、版本、范围、状态、宿主读取端口 |
| `FileContextCoordinator.ts` | 分支工作集、观察顺序、刷新屏障、版本目录和历史召回 |
| `FileSnapshotArchive.ts` | 不可变正文、内容寻址、调用来源、重命名关系、安全分页 |
| `FileContextProjection.ts` | 历史读取回执和当前源码活动尾；无文件 IO |
| Agent `ProviderSendRequest.ts` | 发送前刷新，使用现有预算估算与编译器控制请求容量 |
| Project `agent/ProjectFileContext.ts` | 规范化项目路径、授权读取、最终补丁正文与修改范围提取 |
| Project `Project.tool.ts` | 在原生读取结果物化前登记；事务提交与回滚后发布变化 |
| Workbench / Desktop | 注册项目来源、提供会话存储、保留档案并随会话清理 |

活跃状态由每个执行 tracker / 分支的协调器持有，以 `(workspaceId, path)` 隔离文件。revision 是不透明的版本标识，观察顺序单独递增。父子分支继承来源访问口，各自维护工作集和预算。

PayloadStore 保存三种记录：`__file_snapshot__` 保存版本正文，`__file_observation__` 把调用关联到正文引用，`__file_rename__` 保存已验证的迁移关系。正文是读取/提交时解码后的文本；字节编码与磁盘恢复继续由 Project 事务系统负责。模型的 `N|` 行号前缀不进入正文档案。

## 从工具调用到下一轮模型请求

1. **读 A**：Project 返回与 revision A 绑定的实际正文。框架保存快照及调用来源，登记当前文件与阅读范围。
2. **发送模型**：持久执行历史保持原样。发送投影把旧 `project:read` 正文换成稳定回执，当前文件正文统一放在活动尾，包含版本、行号、覆盖范围和历史引用。
3. **改 B**：内核完成原子事务。框架从最终事务补丁取得实际提交前后的全文，授权、脱敏后归档；受影响的当前文件立即标记待刷新。
4. **刷新 B**：小文件读取全文，大文件读取最终 diff 附近的范围。修改结果继续返回事务 ID、changedFiles、newRevisions、最终 diff；上下文故障使用独立的 contextRefreshError。
5. **下一次发送**：等待待处理更新，并重新验证活跃文件的实际版本。模型直接获得 B 的实际源码、版本和行号，可继续改 C。
6. **召回 A**：通过现有 `context:recall` 返回明确标为 historical 的 A；当前文件仍为 B 或实际更新后的 C。

当前视图的 fresh 表示本次确认时与来源一致。模型推理期间仍可能发生外部修改，后续写入继续由 Project 的版本校验兜底。

## 历史版本召回

支持三种输入：

```json
{ "path": "src/a.ts" }
{ "path": "src/a.ts", "revision": "版本标识" }
{ "refKind": "file-snapshot", "ref": "ctx-payload:..." }
```

只给路径返回可分页的版本目录；给版本或引用返回相应历史正文。全文档案与片段档案明确区分：同一版本只有多个片段时先返回片段引用目录，不把它们拼成伪造全文。分页返回 nextOffset，自动边界保留 UTF-16 代理对和 CRLF。

重命名可以沿已确认的 before/after revision 关系找到原路径快照。当前实现关联直接迁移版本及匹配的连续重命名链；它不是完整的 Git 文件谱系。未被框架观察和保存的外部中间版本无法召回。

召回重新执行当前读取授权与脱敏检查。权限收紧时返回受限状态。损坏的单条档案被隔离，指定其引用时返回损坏原因；有效档案和当前文件刷新仍可继续。召回本身不修改磁盘。

## 大文件、成本与上下文预算

- 每个分支最多保留 100 个活跃文件；在启动读取前裁剪工作集。按最近阅读/修改优先级保留，普通刷新不改变顺序。
- 小文件阈值为 32,000 bytes；大文件每次最多刷新 8 个范围，每个文件共用 64,000 字符读取额度。
- 文件活动尾最多 32,000 字符，同时受当前模型可用窗口 15% 的 token 额度约束；与最终请求门共用预算估算，最终由 ProviderRequestCompiler 准入。
- 投影按优先级选择全文或片段，标明截断、省略文件数与后续读取位置。完整历史档案不受内联窗口大小限制，召回依旧分页。
- 同版本的重复范围去重，完整快照覆盖部分窗口；不同版本片段不能混用。每个片段的历史引用与正文保持对应。
- 大文件修改后，读取最终 diff 的新行号附近范围；旧范围的位置无法确认时重新建立窗口。当前实现不提供任意旧范围的精确行号迁移。
- 每次发送复核活跃文件，不依赖 watcher 或 mtime/size 缓存，因此能发现保留大小及 mtime 的外部修改。该策略会增加文件 IO，测试上限约束不等于已完成长期性能优化。

内容寻址避免相同快照重复存正文。版本查询目前复用 PayloadStore 的会话扫描接口，尚无专用磁盘版本索引；超长会话的档案查询成本、保留配额与缓存命中收益需要后续实测。完整源码档案随会话持久化，宿主删除/清空会话时清理。

## 边界与故障行为

| 情况 | 行为 |
| --- | --- |
| 旧 read 迟到或归档期间发生新修改 | 归档旧结果；按观察顺序保护当前指针 |
| 分页读取中版本变化 | 不合并跨版本正文，标记待确认 |
| 提交 B 后外部程序写 C | 保存实际提交 B，当前视图刷新为 C |
| 删除、回滚、外部修改 | 下次发送前确认实际状态，删除文件不保留当前正文 |
| 提交成功、归档失败 | 返回已成功编辑和独立上下文错误；继续尝试当前刷新 |
| 读取失败或授权拒绝 | 标记 unavailable，移除当前正文 |
| 进程重启 | 按本分支调用来源恢复路径，重新确认磁盘 |
| workspace 切换 | 来源检查内核根路径，避免旧项目端口读取新项目内容 |
| renderer 增量保存 | 主进程文件档案与来源记录继续保留；明确清空时删除 |
| 中文、emoji、CRLF、单独 CR 后的数字前缀 | 正文分页与行号转换保持对应字符，不二次剥离源码内容 |

自动当前视图已接入 Project 的 read、edit、write 和 rollback；执行命令造成的活跃文件变化由发送前复核发现。搜索、语义查询、诊断等结果仍是当时的历史证据，它们的统一版本元数据接入尚未完成。用户消息中的代码及助手既有推理不会被源码投影替换。

## 验收口径

检查实际发给 provider 的请求、原始历史、磁盘文件和持久快照四者的一致性。Workbench 用真实执行栈、Project 内核和磁盘 PayloadStore，在大型 Platform worktree 中运行受控模型的连续调用；该用例可以确定性证明自动注入、无需重复 read、历史召回和重启有效。外部真实模型是否自然使用这套信息，以及缓存命中、费用和长会话延迟收益，需要独立在线任务验证，不能从受控模型结果推断。
