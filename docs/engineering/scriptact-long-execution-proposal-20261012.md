# 长任务执行合同修复

状态：已按用户要求在 main 实施显式执行时限与进程回执保证范围，冻结为 v21；176 项相关回归和真实 125 秒边界控制通过。v22 小时级配对已完成独立审计，双方完整交付均不合格：状态预期与实际输出未充分独立，Runtime 还把固定等待计入有效工作。合格的小时级完整任务仍待完成。

## 实测问题

`roomsync-reliability-validation-01` 第 97 次请求以 `async:true` 启动 75 分钟程序，子进程 timeout 为 4800000 ms，却在 120380 ms 被外层程序终止。第 119 次请求再启动剩余长段，又遇到相同上限。后台执行复用了正常程序的 120000 ms 硬上限，v16 模型接口当时没有申请更长时限的字段。

原始证据位于同一评测目录的 `scriptact/node-program-timeout-diagnosis.json` 与 `scriptact/recovery-preservation-progress-audit.json`。第二次中断后，模型保留失败日志并手工清空三个房间的 journal 尾部。后续只读核查确认，该失败段 24877 条唯一 ack 身份在保留的全部 12 份服务快照/事件日志中均不存在；原命令、成功执行回执和哈希存于 `scriptact/recovery-preservation-confirmed-audit.json`。这是生产者恢复行为，宿主超时清理本身没有清空数据。

现在可以通过多个短段完成工作，但真实构建、迁移或压力程序不一定支持任意切段。v17 补齐时限说明，单次受管 Node 程序仍采用两分钟的计时上限。

2026-10-11 23:09 UTC，第 173 次请求通过 Node 的 `spawn({detached:true})` 和 `unref()` 启动独立压力进程。实际 PID 58472 已被系统托管到 PPID 1，23:16 UTC 仍在运行并持续记录确认事务，证明现有 Node 访问范围内可以跨程序维持 OS 进程。这条路径没有长程序的完整回执，不能据此推断它受 Runtime 取消链约束。

独立本机控制进一步复现了生命周期缺口：相同进程组的子进程在正常退出、超时和取消三种情况下均被清理；`detached:true` 的三个对应实验中，子进程在命令结束和 `host.dispose()` 后仍存活，回执却均为 `cleanupIncomplete=false`，正常退出还返回 success=true。实验使用生产 `createLocalShellHost`，无模型请求，六个子进程均由诊断程序核对身份后清理。证据为评测根目录的 `detached-process-lifecycle-control.{mjs,json,log}`；只对本次 macOS 实测成立。

## 当前执行合同

扩展现有 `exec` 的选项，提供 `timeoutMs`。省略时继续采用现有缺省程序时限；显式请求长时限时，以宿主允许上限与当前父任务剩余时限共同约束。后台程序继续沿用现有 executionId、运行状态、输出回执和取消链。

示例目标行为：`exec({code, options:{async:true,timeoutMs:4800000}})` 能运行实际的长时间子进程；任务总期限较短时按实际剩余期限受理并返回实际时限。取消任务、父任务结束和应用关闭均终止受管执行及其已登记的子进程，保留部分输出与确定的失败回执。对时限的收窄必须可见，调用方可以据此选择分段。

进程归属也必须进入实施设计：POSIX 的当前实现只向原进程组发信号，不能在增加 timeoutMs 后声称所有脱离进程组的后代都已回收。需核对已有后台任务登记和停止合同，明确独立后台进程如何进入宿主管理、保留何种取消凭据，以及无法确认收束时如何报告未知。普通父子进程、脱组进程和跨程序长期服务分别用实际控制验收。当前已实施显式执行时限与进程回执范围：POSIX 标注 process-group/unknown，Windows 进程树回退标注 process-tree/unknown，Windows 原生 Job 标注 job/owned。独立 OS 级脱组后代监督仍是待解决的架构边界。

`observe` 沿用自己的短时采集合同。源码引用只复用代码；本次时限属于调度参数，重新执行须重新指定，不能因引用旧源码继承过大的期限。格式为完整程序 JSON 时保持源码数据与调度字段的现有分层。

此项不承诺应用退出后进程继续存活。跨程序、跨应用恢复仍依赖实际持久状态；中断后不得将效果未知的写入直接重放，也不得把后台受理当作成功回执。

主线 `ActLoop` 的轮次期限目前可以触发封段续跑，首次到期并不直接取消。实现时须区分这一周期与宿主给出的真正任务截止时间；正常上下文换段不能重启已受理程序，真实父任务截止和取消必须终止程序。相关预算继承和续跑竞态纳入下面的验证。

## 具体改动路径

- `act/runtime/types/native-tools.ts`、`types/session.ts`、`utils/script-records.ts` 和 `utils/script-submission.ts`：执行时限字段、两种传输的共同校验与调度数据；负数、零、非有限数和错误字段在派发前拒绝。
- `act/runtime/impl/RuntimeSession.ts`：绑定本次请求时限、当前运行剩余期限和实际 executionId；沿用现有 Agent 总期限取消，显式记录请求值与生效值。
- `script/src/contract/requires.ts`、`impl/KernelScriptSession.ts` 和 `impl/CodeSurfaceSession.ts`：将宿主核准的本次执行时限传至已有 Node runner，保留旧调用方缺省行为与宿主能力停表语义。Node runner 已接受有限的 `timeoutMs`，无需新增第二套进程服务。
- 用正式类型重新生成原生 Schema，更新两种模型传输说明及模块 README，保持生成物与实际执行边界一致。
- `execution/impl/local/ShellManagedProcess.ts`、`ShellProcessManager.ts`、`ShellCommandRunner.ts` 与 `execution/utils/process.ts`：审查实际后台归属与回执范围，复用已有登记和取消入口。新增的脱组实验暴露现有进程组清理的局限；不把范围不明的进程视为已完整回收，也不以进程名匹配代替所有权证据。

## 验收与实际对比

先用真实短进程验证同一生命周期：较长子进程可在显式受理时限内完成，较短程序时限准确停止进程，后台输出仍到达对应执行，用户取消、父任务到期及会话关闭回收声明受管的后代。覆盖无参数兼容、两种协议、观察拒绝、源码引用、错误输入、能力停表和取消竞态；独立脱组案例必须如实反映实际保证范围，不能只有同进程组的正例。

之后运行一次真实超过两分钟的程序验证默认边界与显式长时限；再冻结新候选，在保持模型、源码、题面、预算和评分器一致的条件下运行实际长程任务。新的结果与 v16 失败分开保存。最终仍要求完整交付、原回归、小时级真实执行与独立任务对比，不能由接口测试替代。
