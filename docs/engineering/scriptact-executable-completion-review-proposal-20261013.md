## 问题与实测依据

p-map 首次配对中，VelarOS 正常结束却只有 24/28 功能验收通过。完成复核把“禁止新工作”当作“取消后不会交付已缓冲结果”的证明。v43 加强通用时序指引后，原材料对照仍把同一要求错判通过；六项有效合成案例中新旧也没有正确率差异。

现有 `CompletionReview` 可以读取原文、产物和执行回执，无法自行执行区分两种行为的反例。建议增加可选的独立执行验证口，先证明模型会使用它获得可靠反例，再决定默认启用范围。

固定评测脚本已在真实产物副本中区分上述问题：严格宿主策略下，VelarOS 产物在 39 ms 内触发反例断言，Codex 产物在 37 ms 内通过同一断言。只证明这一项行为；该脚本由评测者编写，尚无模型自主设计反例或完整任务改善结论。

## 拟调整的合同与职责

1. `CompletionReviewOptions` 增加可选宿主执行端口。Runtime 负责需求身份、证据版本、调用预算和审计，Desktop/Node 宿主负责副本准备与进程隔离。
2. 现有 `CompletionEvidenceOperations.retrieve` 保持只读取证语义。新增独立的复核验证操作，明确声明执行效果；TS 操作接口生成模型合同、模板和基线。
3. 验证操作只能引用本次授权产物的身份与哈希，提交验证代码及对应需求身份。宿主决定运行时、参数、可读输入和临时写目录；模型不指定任意宿主命令、环境或路径。
4. 首期支持 Node 验证代码。原始产物复制到执行写目录之外的只读输入区；复制前后核对文件类型、真实路径和完整哈希。依赖使用宿主准备的明确快照，缺失依赖作为验证缺口返回。
5. 回执绑定需求版本、输入清单、完整源码哈希、验证代码哈希、实际退出/信号/超时/取消、输出截断及清理状态。产物变化使旧回执失效，接收结果前再次核对版本。
6. 执行占用同一次完成复核的期限与资源额度，模型请求继续计入父任务及祖先预算；取消或关闭复核须先回收验证进程。只返回有界输出和可追溯回执。

执行断言失败后，复核仍须判断失败属于任务反例、断言错误还是环境缺口。一次通过只支持实际执行的断言，不能据此给全部需求判通过。无法启动、超时、缺失依赖、输出截断和版本不一致保留为明确缺口。

## 宿主边界与原型结果

原型调用已有 v42 进程执行器，所有测试仅接触评测专用文件和专用进程。

| 控制 | 实际结果 |
| --- | --- |
| 同一反例运行真实 VelarOS / Codex 产物副本 | 断言失败 / 通过，原文件与输入副本哈希一致 |
| Node 权限加现有 `ConfinedShellRunner` | 普通越界读写、联网、子进程启动被拒绝，超时和取消回收通过 |
| 现有边界的补充控制 | 可以向副本外专用进程发送信号；现有后端本来就报告 `partial` |
| 默认拒绝的 macOS 原型策略 | 副本外读写、输入改写、外部进程信号、子进程启动、联网均返回 EPERM；临时目录读写成功 |
| 严格策略超时 | 319 ms 返回超时，专用进程已不存在，清理回执完整 |

严格策略的前两次启动在系统加载器中终止，失败日志保留；使用本机 `dyld-support.sb` 后，启动、两份真实产物、边界和超时五项控制通过。该系统文件是私有接口，其哈希单独保存，产品接入需要按实际系统与运行时预检。原型没有认证完整的恶意代码隔离，也没有验证其他操作系统。

Node 自身的 Permission Model 用于约束普通代码行为，官方说明它不是恶意代码安全边界，因此执行能力必须依赖宿主的进程与文件约束。[Node 24.15 官方说明](https://nodejs.org/download/release/v24.15.0/docs/api/permissions.html)。

产品端口要求宿主明确提供可读输入、写范围、网络与进程操作约束，并验证必要能力；不具备所需能力时返回不可用。资源额度、清理、权限更新与撤销由 execution/宿主管理，Runtime 不自己启动裸进程。
