## 差量与合同

- Kernel 将既有 20 张、总 base64 20 MiB、单图 4 MiB 三项限制公开为 `ModelImageLimits`，实际限额不变。
- Images 的单图合同从错误的 5 MiB 对齐到 Kernel 的 4 MiB，超限继续走既有缩图或可恢复单项错误，不扩大权限；声明、生成合同和验收同步。
- Runtime 在组装原生附件时共同计算用户图、执行结果和持续观察的数量及字节。实际已附图的索引用于 required 输出验收；容量未容纳的图片明确标为 `deferred`，不是已看、不是自动待发送队列。
- 恢复沿用已有 `memory.release({ref})` 与 `images.view`：释放占容量的旧执行结果，再按原路径查看下一批。`memory.read` 只是归档 JSON，不替代原生图片。持续观察需要缩小范围或清除；释放执行结果不会清除观察。用户图片占满时应在新任务仅附必要图像。
- 控制提交回执不再重复内嵌已独立归档的附件，幂等重放按原 `resultRef` 还原完整公开回执。只移除回执自身附件字段，业务输出中同名字段原样保存。
- 字节边界回归另外发现：5 张各 4 MiB 的合法图片在 `model-request` 的 request 与 providerRequest 中重复内嵌，产生约 42 MB 单对象，超过 Context 既有 8M 字符限制。大请求审计将像素独立归档，引用携带编码类型和 data URL 前缀，可逐字重建并核验既有指纹；真正发送给模型的请求不变。普通小审计形状不变。纯图片审计不参与业务材料版本判定，不触发整理冲突。
- 提示审查同步移除 `BrowserFillInput` 类型说明中“日期不支持 fill”的旧描述，明确已有 date/time/datetime-local/month/week 原生 setter 与非 trusted 事件语义，与方法说明、实现及既有验收一致；不改变浏览器行为。

- 截图的 width/height 先经已有视口设置链路实际应用，再截图；只给一边时保留另一边实测尺寸及 mobile 模式。设置保持生效，与原合同“截图前把视口设成多大”一致。共用队列内部实现，不递归入队、不改变能力授权。
