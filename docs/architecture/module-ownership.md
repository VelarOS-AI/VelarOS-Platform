# 模块结构：合同、类型、实现、工具函数、入口（仓库标准）

这是全仓库的包结构标准：`packages/system` 最先按它改完，是样板；其余包按同一套逐个纳入（ui 暂不纳入）。每个已治理的包，源码只有五个目录：

```text
src/
  contract/     对外合同：provides.ts 登记产品面（类实现的 API 定义在类上方），requires.ts 注入面，constants.ts 约定的常量表
  types/        只放类型，按域分文件；可移植数据文件随 ./contracts 出包
  impl/         一个工具文件放全部工具，其余一个类一个文件，文件名就是类名
  utils/        纯工具函数，按类别分文件；每个函数上方一句中文说明；登记的 tuning 文件是包内可调参数表
  exports/      对外入口，只转发，package.json 的 exports 指向这里
```

**不拆碎文件。** 一个文件一个职责，内容多没关系；不为了「看起来整齐」把一个职责拆成一堆一两个文件的目录。全部工具的定义连同分组与挂载是一个职责，放一个文件；每个类一个文件；纯函数按类别进 utils。

**文件多了可以分包。** `types/`、`impl/`、`utils/` 文件多时按域开子目录（例如 `impl/transactions/`、`impl/editing/`），子目录里的规矩和上一级一样。每个子目录至少直接放 3 个源文件：一两个文件的不单开目录，也不套一层只装子目录的空目录。`contract/` 和 `exports/` 不分包。分层可以按子目录登记。

人看代码的顺序：先看工具文件（`packages/system` 是 `src/impl/SystemTools.ts`），再看 `contract/` 的三个文件和各类上方的接口，需要时看 utils 里函数上方的一句说明。类的实现、数据字段和工具函数的内部一般不用看。工具文件和两个公开接口文件也由 agent 动手改，但每一轮都要在差量报告里点名，人读懂、复核；其余代码由 agent 维护。

登记表在 `scripts/ownership/governed-modules.mjs`，门禁是 `bun run check:module-ownership`，已在 `check:gates` 链上。第一个进入治理的包是 `packages/system`，它的卡片 `packages/system/MODULE.md` 是样板；第二个是 `packages/platform`，它没有工具，登记表里不填 toolsFile、toolDefiner、hostPort，卡片「骨干链路」写的是每件能力的回答方式。

## 合同、类型、常量分开

`src/` 下五个目录：`contract/`、`types/`、`impl/`、`utils/`、`exports/`。

- **`contract/` 是对外合同**，只有三个文件。`provides.ts` 产品面：交给外面的整件能力——类实现的 API 定义在各自类的上方（`impl/` 里，接口紧挨着类，一起导出），这里用 `export type { X } from '../impl/类文件.js'` 登记；没有类的公开接口（工具集合、内置 mod 定义、能力服务）直接声明在这里。`requires.ts` 注入面：宿主必须或可以塞进来的东西，每个注入点一个接口，写清谁给、什么时候给、必不必须。`constants.ts` 约定的常量表：工具身份与类别、mod 与空间身份、错误码、环境变量表、公开的上限，只放 `Object.freeze` 的表、`as const` 的字符串身份和由它们派生的类型别名。改这三个文件等于改对外契约。
- **`types/` 只放类型**，一个值都没有，只用 type import，只引 types 与合同，按域分文件（`system.ts`、`files.ts`、`commands.ts`…）。出不出包不看文件：合同的签名闭包用到的才从入口导出，实现自己的工作类型（写入计划、准备好的命令、清单印记、带回调的选项）自然留在包内。
- **可移植文件**是 `types/<portable>` 和 `contract/constants.ts`：不 import（可移植类型文件只许从常量表 import type）、不用 Node 专属类型、不带函数成员；`./contracts` 入口就是这两个文件。

| 文件 | 面 | 出不出包 |
| --- | --- | --- |
| `contract/provides.ts` | 产品面：登记类上方的 API，声明没有类的公开接口 | 每个声明与登记都从根入口导出 |
| `contract/requires.ts` | 注入面：宿主要塞进来的东西 | 每个声明都从根入口导出 |
| `contract/constants.ts` | 约定的常量表 | 整个随 `./contracts` 出包 |
| `types/*.ts` | 数据形状与实现的工作类型，按域分文件 | 公开签名用到的才出包 |

类实现的接口一律写在类文件里、紧挨在类的上方并导出；实现文件只许导出这个接口和以类名开头的配套接口（构造参数、回调），其余类型都不许声明在实现文件里；utils 不许声明任何类型。

## 常量分四处

同一个数字只有一个出处。按"谁依赖它、谁会改它"放：

| 常量 | 放哪 | 门禁 |
| --- | --- | --- |
| 对外承诺的：工具名、错误码、环境变量、写进工具说明与 schema 的上限 | `contract/constants.ts`，每个数字一句说明；工具说明里的数字用模板字符串引它，改一处模型看到的跟着变 | 数字上限缺说明；工具定义里写裸数字（示例与 1000、1024 这类单位换算除外）；说明文字里写两位以上的数字 |
| 包内可调的：超时、缓冲、保留条数、缺省条数、阈值 | 登记的 `utils/<tuning>`：一个导出的冻结表，按用途分组，只放数字，每项一句说明 | 每项有说明、每项有人用；impl 与 utils 里不许散写数字缺省值：模块级数字常量、`?? 数字`、参数缺省写数字、名字像超时/上限/缓冲的属性写数字（0 与 1 除外） |
| 某个类里固定用的：文案、模式、名单 | 那个类的 `private static readonly` | impl 的模块级只放日志和导出的实例 |
| 规则本身的数据：危险命令名单、敏感路径名单、搜索跳过的目录 | 跟着规则留在各自的 utils 文件里，改名单和改规则一起审 | 无 |
| 算法与格式里的数字：哈希取几位、编码判定的比例、符号链接最多跳几次 | 就地写，旁边一句说明 | 无 |

包内几处共用的值（列任务的缺省条数、判断二进制时看开头多少字节）只在可调参数表或合同表里写一次。跨包的同名常量不共享代码：包之间互不引用，两个空间各持一份，由仓库层的一致性测试守着（命令策略、沙箱契约）。

## 对外入口由接口控制

不是所有东西都要导出。外面能拿到的只有三样：产品面、注入面，以及它们签名里用到的数据。决策与 `packages/system` 的迁移表见 `docs/decisions/0003-package-contracts-control-exports.md`。

- 入口文件只写转发语句，不写声明。
- 导出的类型只能来自 `contract/`（provides 登记的类上方接口与直接声明的接口、requires、constants 派生的别名）和 `types/` 的公开数据文件。
- 导出的值只能是两种：`contract/constants.ts` 里的常量表，或 `impl/` 里显式标注成公开接口类型的实例与工厂。类、utils 函数、内部接口一律不出包；错误类不出包，外面按错误码判断。
- 公开签名里用到的每个数据类型都要导出；导出的数据类型必须被公开签名用到。可移植数据文件里不放公开签名用不到的类型。
- 注入尽量少且可控：宿主只能从 `requires.ts` 里的口子塞能力进来，别处不留钩子，也不给测试留钩子（类的属性直接挂一个导入的函数、等着测试替换，门禁会拦；要测就直接测那个函数）。宿主端口里只放工具真会调的方法，门禁按工具文件和它委托的 impl 类核对；宿主自己的界面要的能力放到产品面的接口上。环境变量也算注入，全部登记在可移植数据文件的环境变量表里，代码里冒出未登记的变量名就拦。
- 依赖只写在文件头：不许用内联的 `import('…')` 类型和动态 `import()`，否则依赖方向和导出规则查不到。
- `package.json` 的 exports 与 `src/exports/` 里的文件一一对应；卡片「提供什么」列出每个入口、每个导出的值和每个公开接口。

## 分层

实现文件从上到下分层，上层可以调下层和同层，下层不调上层。每个实现文件属于哪一层登记在登记表的 `layers` 里（写文件相对 `impl/` 的路径，或以 `/` 结尾的子目录表示整个子目录），新文件必须先选好层。各包的层次以登记表为准，卡片「结构」一节写明；典型的是「工具 → 宿主 → 能力 → 错误类」四层，工具文件在最上面。

utils 在所有层的下面，谁都可以用；它只引 utils、types 与合同，不引实现。

## 类与接口

实现写成类，一个类一个文件，文件名就是类名。每个类实现一个接口，定义在类的上方（注入面的在 `contract/requires.ts`），这是给人看的：接口本身写这个类负责什么、实例归谁，每个方法写清楚做什么、返回什么、什么时候失败。类的实现一般不用看。

- 类的公开成员只能是接口里的成员；没有公开静态成员。
- 私有方法只放用得到实例状态、没法提出去的公共逻辑；用不到实例状态的函数放进 utils。
- 整个进程只需要一份的类，在文件末尾给出那一份；要出包的那几份按公开接口标注类型。
- 实现文件里的模块级函数只许是对外入口要的工厂，其余逻辑都在类里或 utils 里。
- 继承 `Error` 的错误类没有方法，不写接口。

## 工具函数

utils 放用不着关心内部的纯工具函数，按类别分文件；文件多时按域分子目录，规矩同上。

- 只放函数和常量：不放类、不导出类型、没有模块级 `let`。
- 每个函数上方一句中文说明，写它做什么；人一般只看这一句。
- 只引 utils、types 与合同。需要用某个类时，参数里收它的接口，由调用方传进来。
- 数字缺省值不写在这里，放进可调参数文件；规则本身的名单与算法里的数字留在这里。

## 渲染进程可加载的入口

登记表的 `browserSafeEntries` 列出会被渲染进程加载的入口。这些入口整条值引用链里不许出现 Node 内置模块（`node:os`、`fs` 等）；只给 Node 用的代码放进单独的文件，不和渲染进程要用的混在一起。

## 规矩

1. 全部工具定义在登记的工具文件里，定义工具的函数只在那里被调用。工具文件只放定义：execute 只写简单的一两步（直接调一次宿主端口，最多 4 条语句），实现多的交给 impl 的类，这里一行交给它。
2. `contract/` 只放带中文说明的接口声明、类上方接口的登记和常量表；`types/` 只放类型
3. 类型都进 `types/`，类实现的接口写在类上方并由 `contract/provides.ts` 登记；实现文件除类上方接口外不导出类型
4. 一个类一个文件、文件名即类名，工具文件不放类；类按上面的规矩对应接口；按登记的分层引用，下层不许引上层。
5. utils 只放带中文说明的函数和常量，只引 utils、types 与合同。
6. 对外入口由接口控制，按上面「对外入口由接口控制」一节。
7. 登记为渲染进程可加载的入口不碰 Node 内置模块。
8. `src` 根上不放源文件，`src` 下只有登记的五个目录；`types/`、`impl/`、`utils/` 可以分包，每个子目录至少直接放 3 个源文件。
9. 常量按上面「常量分四处」一节放。
10. 每轮结束交差量报告。

以上每一条都由门禁机械核对。

## 差量报告（每轮结束交这个）

```text
差量报告：<模块>

工具改动（逐个工具）：
  <工具名>：改了什么 / 为什么 / 影响谁
  （没有就写「无」）
需要人拍板的项：
  （提示词或审批语义变更、provides 或 requires 的增删改、入口增删、已有验收用例改口、新增依赖；没有就写「无」）
不变量：通过 x / 共 y（未验证 z）
验收测试：通过 a / 共 b
实现测试：通过 c / 共 d
其余改动（一句）：
```

## 共用与重复怎么处理

- **包内的重复，收成单源。** 同一个类型、同一份名单、同一个测试假对象只写一次：数据结构进 `types/`，名单进它所属的 utils 文件，假对象进 `spec/support.ts`。根入口只做并集转发，不重抄名单。
- **包与包不互相引用源码，测试也不行。** 空间之间（system、project）互不知道对方；一个包的测试要用到别的包，就放到仓库层的 `tests/<域>/`（挂在 `test:suites`），经对方的入口引用。
- **跨包的相同逻辑，抽成公共包。** 两个包写着同一段逻辑（危险命令判定、文本文件编码与原子写入、沙箱契约这类），抽到一个按含义命名的公共包里，两边都依赖它，不再各持一份镜像；公共包同样按本标准治理。域无关的原语去 `@velaros-ai/core`，跨平台兼容去 `@velaros-ai/platform`，其余按含义新建，一包一义，不做杂物包。
- **抽不出去的镜像，才用一致性测试守着。** 两边只是形状相同、逻辑不同（比如两个空间各自的工具入参），各持一份，用仓库级测试核对它们对同样的输入给出同样的裁决。

## 把一个包纳入治理

1. 先定合同：这个包交出去哪几件整件能力（API 定义在各自类的上方，`contract/provides.ts` 登记），宿主要塞进来什么（写进 `contract/requires.ts`），约定哪些常量（`contract/constants.ts`），它们的签名里流过什么数据（写进 `types/`）。每个接口、每个成员写中文说明。
2. 把全部工具定义收进 `src/impl/` 下的一个工具文件，连同分组与挂载；每个工具上方一行注释，说明、参数、权限都在定义里；execute 只写简单的一两步，实现多的交给 impl 的类。工具说明里的数字引 `contract/constants.ts` 的常量表。
3. 有状态、有一组相关操作的逻辑收成类，一个类一个文件放在 `src/impl/`（文件多就按域分子目录），文件名即类名；类实现的接口写在类文件里、紧挨在类的上方（公开的在 `contract/provides.ts` 登记），其他工作类型写进 `types/`；用不着实例状态的纯函数收进 `src/utils/`，每个函数上方一句中文说明。常量按「常量分四处」放，可调参数进登记的 tuning 文件。
4. 入口放进 `src/exports/`，只转发产品面、注入面和它们用到的数据；`package.json` 的 exports 指过去。
5. 写卡片 `MODULE.md`：「提供什么」列出每个入口、每个导出的值和每个公开接口，「骨干链路」列出每个工具的链路，「结构」写明目录树、分层和每个类的接口。
6. 登记表加一行：工具文件、每个实现文件（或子目录）的层、可调参数文件、会被渲染进程加载的入口、环境变量表。跑 `check:module-ownership` 到绿。
