# 模块说明规范

每个登记模块只有一份说明：模块根目录的 `README.md`。普通包的根是包目录，Velaros 的能力单元与 Act 职责组是单元目录，Core 的底层单元是 `src/<单元>/`。子目录里不放说明文档，MODULE.md 已经取消。一个包里有几个单元时（Velaros、Core），包根的 README 只做索引：包是什么、有哪些单元（一行一句），细节链接到单元 README。

读者是要用这个模块的人：产品宿主、别的包、第三方。文档只写从代码和配置里看不出来、用的人又必须知道的东西。

## 不写什么

下面这些都有唯一出处，文档里再写一遍就会和出处对不上：

| 内容 | 出处 |
| --- | --- |
| 导出了哪些值和接口 | 入口文件与 `contract/provides.ts` |
| 目录结构、分层 | `scripts/ownership/governed-modules.mjs` 与所有权门禁 |
| 依赖 | `package.json` |
| 不变量与条数 | `spec/invariants.md` |
| 内部类名、调用链细节 | 代码与注释 |
| 为什么这样改、改造过程 | `docs/engineering` 下的差量文档 |

## 结构

```markdown
# @velaros-ai/<包>[/<单元>]

一两句：它做什么，给谁用。

## 用法

最小可用示例：从公开入口 import → 装配 → 调用 → 处理结果与失败。

## 入口

| 入口 | 运行环境 | 内容 |
| --- | --- | --- |
| `@velaros-ai/<包>/<子路径>` | Node / 任何进程 / 渲染进程 | 一句话 |

## 约定

- 调用方必须知道、类型签名里看不出来的约束，一条一句：失败码与怎么处理、上限、谁持有状态、谁负责关闭、取消与并发、明确不做什么。
```

- **用法**必有，至少一段 `ts` 代码块。示例只从公开入口 import；宿主提供的东西写成 `declare const storage: ContextStorage` 这样的声明。门禁 `check:readme-examples` 按真实公开类型对每段示例做类型检查，示例跟着代码一起变。
- **入口**必有，列出这个模块在 `package.json` 里的每个公开子路径，写完整的 import 名。
- **约定**可选，没有必须知道的约束就不写这一节。
- 不写其他小节。要讲清楚的设计放进 `docs/architecture`，在约定里链接过去。
- 一份 README 不超过 160 行。写长了先看是不是在复述代码或者在讲历史。
