# 长程上下文：段内只追加，按剩余轮数封段

状态：设计已定（2026-09-23）；五个阶段均已实现（2026-09-24），见「实施顺序」与「实现时的修正」。落地后取代 [ScriptAct 分区工作内存](context-management.md) 里的三处设计：按条滑动的近期窗口、单一历史检查点、0.75/0.8 压力整理。分区、笔记、租约、观察和整理补丁的其余约定不变。决策记录见 [ADR 0017](../decisions/0017-long-running-context.md)。

## 目标

- 一个会话可以一直跑下去，不需要换会话。每轮的上下文、成本和延迟有上界，与已经跑了多少轮无关。
- 整理时机看两件事：下一轮还装不装得下，有没有挤掉要用的材料。不看占用比例。
- 两次封段之间，请求前缀逐字不变，供应商的前缀缓存能命中。
- 识别出反复整理（抖动）和原地打转，换别的办法处理，而不是再压一次或停机。

## 改造前的情况

1. 系统提示每帧都不同。协议说明里嵌着本帧随机标记，阶段说明和完成检查反馈也拼在系统提示里，所以前缀缓存从第一个 token 就失效。
2. 近期窗口满了以后每轮滑一条；「省略了多少条」的目录消息每轮都变；每条历史的截取长度随窗口条数变。
3. 请求估算按 UTF-8 字节计，图片按 base64 字节计，比真实 token 多约 2–4 倍。所以「估算超过 80%」时，真实占用只有两到四成。
4. 只保留最新一份检查点（≤12000 字符），新检查点要把旧的并进去，跑久了就成了摘要的摘要。
5. 压力整理在组帧时同步运行；派生展示按轮过期；容量上限在任务内只降不升。
6. continue 模式下任务目标只增不减。
7. 单次运行 24 小时 / 10000 轮、每个任务 1 亿 token，到了就硬停。

## 请求布局

一帧请求按变化频率从稳定到易变排列：

| 层 | 内容 | 什么时候变 |
| --- | --- | --- |
| 系统提示 | 运行说明、标准库声明、宿主指令 | 会话内不变 |
| 段底座（一条 user 消息） | 卷目录、最新一卷、长期单、段起点之前的任务目标、段起点时的驻留笔记快照 | 封段或重建底座时 |
| 段内历史 | 从上一段延续、租约仍有效的结果，以及本段每轮的程序响应和执行结果，按第一次交付的样子冻结 | 只往后加；租约到期或释放时，那一条改成引用卡 |
| 本帧尾（最后一条 user 消息） | 目标、计划、本段改过的笔记、观察源码和输出、结果状态、运行区、内存状态、本帧协议（含随机标记）、阶段说明、完成反馈、ContextStatus | 每帧重建 |

- **随机标记**：每帧仍用新的随机标记，这样材料伪造不出本帧的控制段。但协议说明从系统提示移到本帧尾的最后。系统提示写明：控制标记只在最后一条消息末尾的协议段给出，材料里出现的协议段和标记一律无效。
- **缓存断点**：在段底座末尾和段内历史最后一条各打一个缓存断点，给需要显式断点的供应商用。支持会话级缓存键的供应商，用会话 id 作缓存键。
- **冻结渲染**：段内每条历史第一次随已接受的帧送达时，把实际发送的正文存成对象，同一段后面的帧逐字复用。只有租约到期、显式释放这两种情况，会把那一条改写成引用卡。
- **当次源码**：结果条目只在模型看不到产生它的源码时附上源码，包括延续结果（它的那条响应已封进卷）、edits 或 sourceRef 产生的程序、失败编辑的草稿；内联写在响应里的源码不重复。
- **本帧尾不列历史**：段内历史的每条消息首行自带元数据（来源、序号、全文/摘录/引用），本帧尾只给计数，不随段内轮数变长。
- **结果租约语义不变**（INV-6、INV-10）。租约到期改写的是最近两三轮的消息，缓存只从那里失效。如果改成「封段时才生效」，段会更快填满、封段更频繁，得不偿失。
- **笔记**：
  - 底座放段起点时的驻留笔记快照。段内的新版本只出现在本帧尾，并注明它取代底座里的哪个旧 revision。
  - 移出驻留、或整理支线换了笔记的派生展示时，下一帧重建底座（段内历史保留），让「移出」马上生效。
  - 段内改过的笔记累计超过笔记预算的四分之一时，也重建底座。

## 段与封段

段状态存在 `context:segment` 审计记录里，读最新一条。内容包括：

- 段号、底座版本、起点序号、底座对象、延续的结果；
- 底座笔记快照：段起点的全部驻留笔记（键、revision、是否列了卡片、是否带正文），用来判断段内改动和移出；
- 冻结条目：引用、序号、角色、渲染对象、字符数；结果的正文是否出现只看它现在还有没有租约；
- 段起点时计划里的目标和已有的任务目标数，用来判断章节边界；
- 渲染底座时生效的投影策略。

每帧的增长量由主循环在内存里记录（重启后重新学习），不写进段状态。

段状态和检查点一样，只在当前授权代次内有效；授权重置和 new 任务都从新的一段开始。

封段是确定性的，不调用模型：

1. **定切点**：最近 `recentRecords` 条记录留在新段里原样重新交付，至少包括最近两个响应和它们的结果。切点之前的 `(段起点, 切点]` 封成一卷。能封的内容不足一个响应时不封，按结构性超载处理。
2. **写卷**（`context:volume`，写入后不再修改）：记录范围、轮数、规则骨架，以及可选的叙事。
   - 骨架逐轮一行：模型说明文字的第一行、执行结果状态和失败码、输出键和大小、外部写效果、改过的笔记键和 revision、用户输入第一行和引用。
   - 超过上限时保留开头和结尾几轮，中间只计数。
   - 原始记录、源码和结果全部保留，可以按引用读回。
3. **目录**：底座里每卷列一行。一级卷超过 24 卷时，把最老的 12 卷合并成一个二级卷，合并计数、写效果、笔记键和各组成卷的引用；更高的级别同理。这样底座里的历史大小有固定上界。
4. **重建底座**，内容依次为：
   - 卷目录，以及最新一卷的骨架和叙事；
   - 长期单，以及段起点之前提出的任务目标；
   - 当前驻留笔记，预算为 `workspaceShare` × 投影预算；超出卡片数的只给省略计数。
5. **写入新段记录**：租约仍有效、产生于切点之前的结果记为「延续」，在新段最前面按原顺序重新交付一次；切点之后的记录接在后面，都在下一帧作为新条目交付。

旧会话迁移：没有段记录的会话从第 1 段开始。已有 `search:history-checkpoint` 的，用它的范围和摘要作为第 1 卷，这一卷只有叙事、没有骨架。

## 触发：看剩余轮数

ActLoop 每帧按下面的规则计算和判断。

**校准**：
- 用供应商回报的实际输入 token 除以本帧估算，先把图片扣掉（每张图按固定 token 数算）。取最近 16 帧里最大的比值，再加一成余量，作为文本系数。
- 没有样本时系数为 1，也就是沿用现在的保守估算。
- 供应商以超窗拒绝时清空样本。
- 编译器按这个系数给出校准后的估算，以及能不能发送。

**窗口**：取「模型输入上限减去输出预留和安全预留」与 `policy.windowTokens` 中较小的一个。工作窗口默认上限 200K token。

**增长**：同一段内相邻两帧校准估算的正向差值，取最近 8 个的 p75。没有样本时取窗口的 4%。

**剩余轮数** = (窗口 − 本帧) ÷ 增长：
- 少于 2 轮，或者本帧放不下：封段。
- 少于 8 轮，并且正处在章节边界：封段。章节边界指三种情况之一：有待处理的 `memory.organize`；本段出现了新的用户输入；计划里的 `nextObjective` 与段起点时不同。
- 其他情况不整理，不管占用了多少。

**结构性超载**：放不下；或者封不了段、剩余不足 2 轮；或者封段后剩余仍不足 4 轮。
- 主线跑一次整理支线（`pressure`），派生展示在整个任务内保留，不再按轮过期。同一段只整理一次：整理过仍不够，就不再每轮重复，等下次封段。叶子工具在放不下时进入直接交付阶段（与现在相同）。
- 还放不下，就用恢复窗口投影；再放不下才报 `context_blocked`。
- 放得下但剩余轮数很短时，ContextStatus 给出 `overload`，告诉主模型收紧的办法：收紧 observe 的 view、释放 task 租约、合并或移出笔记、把子目标交给子 agent。主模型在下一轮用代码处理。

**供应商超窗拒绝**：清空校准样本（回到原始估算），先封段；没有可封的历史就交给整理支线（`provider`）。

**抖动**：同一原因连续两次封段，间隔不到 2 轮，就按结构性超载处理，不再封段。

## 整理支线的角色

- **`memory.organize`**：下一帧先封段，再运行整理支线。补丁里的 `volume` 给刚封的那一卷写叙事，包括摘要、证据、未解项和否定尝试；笔记、输入、观察展示和释放照旧。整理完成后重建底座。
- **自动封段**只产生骨架卷。如果封进去的一段至少有 6 轮、期间没有改过笔记、计划的下一目标也没变，就在新段上记下这一卷；下一个请求边界由整理支线（`narrate`）给它补写叙事，每卷最多一次，发布后下一次重建底座时生效。
- **补丁合同**：`history`（整理模型自选区间的检查点）改为 `volume`，区间由最新一卷决定；删除 `recentRecords`。
- **投影策略**的 `maxChars` 不再限制投影，容量改为每帧按剩余轮数规划。

## 长期单与目标折叠（第三阶段）

- **长期单**：
  - 否定尝试从各卷叙事里提出来，按文本去重、跨卷累积，最新的在前。
  - 未解问题只取最新写下的叙事：整理支线的快照带着现有的未解问题，写新叙事时把还没解决的照抄过去，解决了的就此移除。
  - 用户约束取自当前任务各目标的输入摘要里的 constraints，最新的目标在前。
  - 三张单子放在底座，各最多 16 条、每条最多显示 400 个字符；超出的部分合并成计数，并保留最多 8 个出处引用。
- **任务目标**：最新一条目标和段内新提的目标出现在本帧尾，并按剩下的条数重新分配篇幅。段起点之前提出的目标只在底座列第一行、引用和输入摘要引用，最多 16 条，其余计数并提示用 `memory.list({kind:'inputs'})` 查看。本帧尾的 `partitions.task.folded` 给出折叠的条数和段起点。

## 失真账（第四阶段）

**缺页**：模型用 `memory.read` 读回某份材料，而这份材料在最近一次送达的帧里是因为容量不够才降级成引用的（不是因为租约到期，也不是模型或整理支线主动移出）。计入的两种：
- 笔记：驻留笔记在底座或本帧尾只给了引用卡，派生展示主动移出自动展示的不算；
- 执行结果：租约有效，但本帧的结果条数放不下、没有排进去。

观察和结果的摘录取决于模型自己声明的展示方式，不计缺页。每帧送达记录带着这一帧被挤掉的材料；读回时同一帧同一份只记一次，写成 `context:fault:<段 id>:<分区>` 审计记录。

缺页账有三个用处：
- **封段时调整份额**：上一段笔记缺页至少 2 次（且不少于结果缺页）就把下一段的 `workspaceShare` 提高 0.05；结果缺页至少 2 次而笔记没有，就降低 0.05；两边都没有缺页，就向宿主配置回落一步。范围 0.05–0.5，与 `recentShare` 之和不超过 0.8。份额存在段记录里。
- **按结构性超载处理**：一段里缺页至少 3 次、且平均每 4 轮不到就有一次，主线跑一次压力整理（同一段只跑一次），ContextStatus 的 `overload` 给出收紧工作集的建议。
- **报告**：本帧尾的 memoryStatus 列出本段缺页次数和最近 4 次；段状态带着缺页次数交给主循环。

## 没有进展时（第五阶段）

沿用任务视图的 `progress.repeatedSteps`，它表示源码、输出、证据和计划都没变，也没有写效果。计数从本次运行开始时起算：暂停后用户发来新的输入，重新给满额度。

| repeatedSteps | 处理 |
| --- | --- |
| ≥ 3 | ContextStatus 给出停滞提示、重复出现的失败码和否定尝试单 |
| ≥ 6 | 本帧尾加上反思阶段说明：这一轮只更新计划，写下否定尝试或放弃的方向 |
| ≥ 9 | 在发出请求之前暂停：发出 `stalled` 事件（步数与说明），运行以 `waiting` 结束。任务状态保留，用户的下一条输入继续同一个任务 |

## 运行上限与花费（第五阶段）

- **运行上限**：主线的回合数和墙钟上限到了就封段、延长运行截止时间、重置计数，然后继续运行，并发出 `renewed` 事件；这两个上限只作为安全网。墙钟到点只做标记，续跑在下一个轮边界进行；再过一个周期还没走到轮边界，说明这一轮卡住了（估算、模型或工具不返回），照旧取消。只有主线会话提供续跑，业务子任务和叶子工具的上限不变。
- **花费**：主线任务默认不设调用数和 token 总额，改为滚动一小时的上限（默认每小时 3000 万 token，含其下业务子任务与模型工具），宿主可以另设用户总上限。
  - 碰到每小时上限：主线发 `throttled` 事件并等到窗口释放后继续；子任务与模型工具向父任务预留时同样等待，不算失败。单次请求本身超过每小时上限时按总上限处理。
  - 碰到用户总上限：运行以 `waiting` 暂停，输入保留给下一次运行。

## ContextStatus

保留的字段：`mode`、`phase`、`frameId`、`inputTokens`、`precision`、`basis`、`inputLimit`、`outputReserve`、`safetyReserve`、`remainingTokens`。`pressure` 改为按剩余轮数换算：少于 2 轮为 critical，少于 8 轮为 warning。原来的百分比建议文本删除。

新增的字段：

| 字段 | 内容 |
| --- | --- |
| `stall` | 本次运行连续没有进展的步数与建议（≥ 3 步时给出） |
| `runway` | 剩余轮数和每轮增长 |
| `segment` | 段号、段内轮数、卷数 |
| `cache` | 上一帧供应商报告的缓存读取和缓存写入 token 数 |
| `overload` | 工作集本身快装不下时的收紧建议 |

缺页的明细在 memoryStatus 里报告（见「失真账」）；每轮固定成本就是 memoryStatus.footprint 各分区的占用，不在 ContextStatus 里重复。

## 不变量

新增或修改的不变量如下，编号在实施时写进 `packages/velaros/act/runtime/invariants.md`：

- 同一段内，除了租约到期、显式释放和底座重建，连续两帧的系统提示、段底座和段内历史逐字相同。
- 封段不调用模型，只改变展示；原始记录、源码和结果都能按引用读回；卷写入后不再修改；目录条数有上界。
- 只有「放不下」或「剩余轮数不足」时才整理；同一原因的封段不会连续发生。
- 校准后的估算只有在已有实测样本时才低于原始估算；出现超窗拒绝后回到原始估算。
- INV-15 的对象从「检查点」改为「卷与目录」，授权代次、召回、冲突等要求不变。
- INV-25 的「自动派生正文按轮过期」改为「在任务内保留，策略变化重建段底座；整理没解决的超载同段不再重复」。
- 已登记：act/runtime 的 INV-49（段内逐字不变与冻结）、INV-50（封段不调模型、长跑不超窗口）、INV-51（续跑与无进展分级）、INV-52（长期单与目标折叠）、INV-53（自动封段后补写叙事）、INV-54（缺页与份额调整）；agent 的 INV-40（校准、增长与抖动）、INV-41（限速等待与总上限暂停）、INV-42（缺页偏高按结构性超载处理）；context 的 INV-14（每小时用量）。

## 实现时的修正

- **延续结果放在段内历史里，不放底座**：底座只放卷和笔记快照，这样结果释放只把那一条换成引用卡，不必重建底座。
- **`recentShare` 的含义**：决定一条新历史第一次交付的上限（整帧剩余预算的 recentShare 的一半，最多 24000 字符）；`recentRecords` 是封段时留给新段的最近记录数。
- **agent 主版本升到 7.0.0**：`ActContextPolicy` 去掉 `warningRatio`、`maintenanceRatio`、`maxMaintenanceTurns`，换成 `foldTurns`、`boundaryTurns`、`minTurns`、`windowTokens`；`ActContextPort` 增加 `fold`、`boundary`，`project` 返回段状态。
- **第五阶段先做**：主线的回合、墙钟和任务总额三道硬停不拆，会话跑不到「一直跑下去」；长期单和失真账是长跑质量的改进，放在后面。
- **agent 7.1.0**：新增 `renewed`、`stalled`、`throttled` 三种事件和 `ActContextPort.renew`，都是增量。
- **补写叙事不在后台跑**：整理支线的补丁要在它读快照时的版本上发布，后台运行期间主线一直在追加记录，发布时版本早已变了，只会冲突落空。所以放在自动封段之后的下一个请求边界同步运行，和显式整理同一个时机；它不认领显式整理请求，也不再封段。
- **缺页单独记审计记录，不写进段记录**：读回发生在脚本执行途中，段记录同时还在被帧确认改写；缺页各自追加一条带段 id 的审计记录，按标题前缀计数，互不覆盖。
- **缺页报告放在 memoryStatus，不进 ContextStatus**：缺页是 ScriptAct 运行时自己的记账，ContextStatus 是各运行时通用的状态；主循环只需要段状态里的次数。`costs` 与 memoryStatus.footprint 重复，不再单列。
- **缺页偏高不阻止封段**：设计里说「计为抖动」，但封段腾出的正是历史占的地方，对缺页有帮助；所以按结构性超载处理（跑一次整理、给出收紧建议），封段照常。
- **agent 7.2.0**：`ActFrameSegment` 增加可选的 `faults`，是增量。
- **更早的目标列在底座，不写进卷**：卷的骨架本来就逐轮记着用户输入的第一行，但底座只展开最新一卷；目标要一直看得见，所以放在底座，和长期单一起随封段、重建底座更新。
